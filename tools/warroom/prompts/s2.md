#927 Stage 2 진행해

War Room이 지정한 Part (Shard {{shard}} · Batch {{batch}} · Part {{part}})를 처리한다.
현재 worktree와 브랜치 {{branch}}를 그대로 사용한다.
Part를 다시 선정하거나 브랜치를 변경하지 않는다.
War Room이 준비한 HEAD를 기준으로 작업하며,
편집 도중 master가 갱신되어도 현재 브랜치를 merge/rebase/reset하지 않는다.

Issue #927의 Stage 2 admission 계약과 docs/relation-factory.md, docs/relation-editorial-policy.md를 읽고 준수한다. 새로운 후보 발굴은 하지 않는다.

절차는 다음과 같다. 셸 명령은 개별로 실행해 각 종료 코드와 출력을 확인한다.
1. `node scripts/relation/admission-cli.mjs prepare --shard {{shard}} --batch {{batch}} --part {{part}} --checkpoint .warroom-scratch/relation-admission-{{shard}}-{{batch}}-{{part}}.json` 를 한 번 실행한다. 동일 checkpoint가 있으면 새로 만들지 말고 재개한다.
2. 모든 후보를 새로 발굴하지 않고 이 Part의 후보만 처리한다. `node scripts/relation/admission-cli.mjs read-chunk --checkpoint .warroom-scratch/relation-admission-{{shard}}-{{batch}}-{{part}}.json --out .warroom-scratch/active-chunk.json` 으로 다음 청크를 읽는다. `complete: true`면 `optional_links`를 살핀다. 기존 ID 관계로 accounting이 끝난 후보는 새 판정을 강제하지 않지만, 남은 target sense와 의미가 실제로 맞는 추가 관계가 있을 때만 `read-chunk --checkpoint <checkpoint> --source-sense-id <id> --candidate <text>`로 열어 선택한다. 추가 링크를 저장한 뒤 `read-chunk`를 다시 실행해 남은 선택지가 있는지 확인한다. 선택할 추가 링크가 없으면 5단계로 간다. 청크는 여러 완전한 source sense를 포함할 수 있다. 한 sense가 기본 250개 후보보다 클 때만 정확한 candidate 시작·끝 위치로 이어진다.
3. 청크의 각 후보를 **한 번에 통합 판단**한다: 신규 Relation 또는 실제 Drop, 각 Relation의 type과 같은 출발 sense/UI 그룹 기준 relevance, exact target ID 또는 text-only를 함께 결정한다. `same_spelling_targets`에는 같은 표기의 모든 record/sense ID·lemma·POS·전체 gloss가 있다. 출발 sense와 모든 대상 sense를 비교하고 첫 항목을 자동 선택하지 않는다. ID 링크는 정확한 target record/sense와 정·역방향 type/relevance를 각각 적는다. 같은 표기의 target sense가 있으면 Relation decision에 `target_resolution`을 명시한다. text-only는 `no_exact_match`와 해당 후보의 target sense ID 전체를 `checked_target_sense_ids`에 적고, exact ID는 `exact`와 선택한 record/sense ID를 적는다. target이 아예 없으면 target 판정 필드는 생략한다. Drop은 실제로 무관한 후보만 선택하고 이유를 쓴다. Type/Tier 기본값, 일괄 text-only 판단, 독립 ID 패스/Tier 패스, 후보 재발굴을 하지 않는다.
4. 모든 후보 decision을 `{"chunk_id":"...","decisions":[...]}` 형식의 `.warroom-scratch/decisions.json` 에 한 번에 기록한다. 각 decision은 원본 `source_sense_id`와 정확한 `candidate`를 보존한다. `node scripts/relation/admission-cli.mjs save-chunk --checkpoint .warroom-scratch/relation-admission-{{shard}}-{{batch}}-{{part}}.json --in .warroom-scratch/decisions.json` 으로 저장한다. 활성 청크가 끝날 때까지 2–4단계를 반복한다. 저장 전 누락·중복·범위 밖 후보, 미판정 target, 역방향 판단 누락은 도구가 거부한다. 중단되면 같은 checkpoint의 pending 청크 또는 다음 미판정 후보부터 재개한다.
5. `node scripts/relation/admission-cli.mjs merge --checkpoint .warroom-scratch/relation-admission-{{shard}}-{{batch}}-{{part}}.json` 로 완성된 decision을 검증한 뒤 기존 Relation/Drop 샤드 파일에 누적한다. merge가 decision을 거부하면 파일은 기록되지 않고 checkpoint가 보존된다. 오류가 가리킨 저장 decision은 `read-chunk --checkpoint <checkpoint> --source-sense-id <sense-id> --candidate <text>`로 다시 열고 `save-chunk`로 수정한 뒤 merge를 재시도한다. merge 성공 뒤 `node scripts/relation/admission-cli.mjs verify --shard {{shard}} --batch {{batch}} --part {{part}}` 를 실행한다. 이미 승인된 행과 다른 Part 행은 보존한다. 다른 샤드·Candidate 파일·Canonical은 수정하지 않는다.
6. 커밋·push하고 Stage 2 PR 하나를 제출한다. **Stage 2 PR에는 `batch` 라벨을 붙이지 않는다.** PR 생성 직전 같은 샤드의 열린 Stage 2 PR이 없는지 확인한다. PR 본문에서 #927을 참조하거나 닫지 않는다.

PR 제출 후 종료한다. 리뷰·머지 감시, 머지 후 최신 master 검증과 다음 Part 실행은 War Room이 담당한다. 다른 모델·CLI·서브에이전트를 실행하지 않는다.

임시·스크래치 파일(검증용 스크립트, 청크, probe 결과 등)은 worktree 안의 `.warroom-scratch/` 에만 만든다. 이 디렉터리는 git에서 무시되며 커밋하지 않는다.
산출물이 아닌 파일을 worktree의 다른 경로에 남기지 않는다.
