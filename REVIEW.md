# Typewriter PR Review

This root `REVIEW.md` is the **authoritative gate policy**. Read it from the **latest PR HEAD** before every review; never read `AGENTS.md`, personal/global `MEMORY.md` or agent memories while reviewing. Producer/implementation issue execution instructions do **not** define reviewer tool procedure; inspect linked task acceptance requirements only when materially relevant under Section 4. Review the reported problem **and the validity of the approach**. Use the smallest sufficient evidence; required correctness is non-negotiable, **but speculative safeguards must not override recurring production speed and AI token efficiency**.

## Production efficiency review

**For repeated production, speed and AI token cost are first-class review criteria.** Reject unnecessary checks, receipts, per-item CLI calls, and repeated reads/hashes/writes unless they prevent a demonstrated defect. Preserve required semantic quality and existing final validation/CI. Judge optimizations against the **previous working path** using actual production time and tokens; more safeguards alone are not an improvement.

## 1. Enter and select exactly one stage

1. Identify the current 40-hex PR HEAD, base, linked issue/acceptance criteria and owner decisions, **complete changed-path list**, earlier review markers/SHAs and unresolved blockers. Read this root file **at that HEAD**.
2. **Stage 1 — focused technical/data review:** when there is no effective same-HEAD `+1` (or a later `-1` reopens the gate), apply Section 2's focused initial or follow-up review. Return `+1` or `-1`; do not inspect CI or merge.
3. **Stage 2 — final HEAD/CI gate and squash merge:** require a substantive same-HEAD Stage 1 `+1`, no unresolved blocker and successful required exact-HEAD CI, then perform expected-HEAD squash merge. Do not conduct another technical review or initiate extra probes; pending CI waits at this gate.

A new commit makes earlier Stage 1 PASS markers **stale**, not previously verified reasoning: Stage 1 verifies the changed HEAD within its focused follow-up scope. Bare markers or evidence-free reviews do not count. The same account may perform the two stages only in **separate runs/contexts**.

**Scope:** PR review Stages 1/2 are separate from Relation Factory production Stages 1/2/3. Preserve earlier review evidence, author responses and unresolved blockers. Stage 2 requires a current-HEAD Stage 1 `+1`; do not demand dummy commits or repeat completed technical work.

**PR changed-path and deletion evidence (all stages):** Determine actual PR scope from GitHub's **complete PR changed-file list** or a **merge-base → PR HEAD** diff, such as `git diff --name-status <base>...<HEAD>` (three dots) or `git diff --name-status "$(git merge-base <base> <HEAD>)" <HEAD>`. Do **not** infer that a PR deleted or modified an artifact merely because it is present on a newer base/`master` but absent on a branch forked earlier; a two-endpoint `git diff <base> <HEAD>` or raw branch file comparison can incorrectly report such **base-only additions** as deletions. Before marking `-1` for deleted Candidate JSONL or other missing files, confirm the path is **actually marked deleted in the PR diff**, check the merge base and exact reviewed HEAD, and establish the real impact. If diff sources disagree, resolve the ref/merge-base discrepancy instead of escalating an unverified absence to a blocker. On re-review, compare old reviewed HEAD → new HEAD separately for fix regressions; that incremental comparison does **not** replace the merge-base-based PR scope.


PR descriptions and issue progress comments are not authoritative review evidence; the latest HEAD's code and artifacts are. **Missing, incomplete, inconsistent or outdated PR-body information is non-blocking feedback, even if the linked method issue specifies a required PR summary.** Never submit or retain `-1`, withhold a technical `+1`, or demand a dummy commit **solely** for a PR description correction; record the focused correction as a non-blocking instruction and issue the technically warranted PASS. A real, independently demonstrated failure of required production, provenance, validation or output remains a blocker; the missing description is not evidence that the work was omitted.

**Author-response obligation on every re-review:** regardless of whether the trigger is a new HEAD or a new comment, inspect relevant PR conversation comments and inline review-thread replies from the author since the preceding review. Evaluate every substantive correction, explanation or rebuttal to an earlier blocker against the current HEAD's code/artifacts and owner decisions; comments are arguments to verify, not authoritative technical evidence. Explicitly accept or rebut each disputed blocker with reasons. If the prior `-1` was mistaken or the blocker is resolved, replace that judgment with a new evidence-bearing technical `+1`, **even on an unchanged HEAD**; never require a dummy code change. If retaining `-1`, address the author's actual counterargument and identify the concrete remaining failure rather than repeating the previous claim.

**Converge rather than repeat:** reviewer and author are collaborators seeking the correct outcome, not opponents defending earlier positions. On each exchange, acknowledge verified points, narrow remaining disagreements to concrete requirements or evidence, and identify the next actionable resolution. Reconsider partially valid objections and adjust the proposed fix or verdict accordingly. Do not restate an answered claim without new evidence or a specific explanation of why the reply fails. If discussion makes no substantive progress, summarize agreed facts, disputed evidence, remaining risks and the decision needed, then escalate to the owner rather than cycling indefinitely. Escalation never authorizes PASS while a confirmed blocker remains; there is no arbitrary limit on productive exchanges.

## 2. Stage 1 — focused technical/data review

**Aim for 1–3 minutes on routine PRs, not a deadline.** Apply the focused scope below; expand only for a concrete doubt or demonstrated blocker. Never conceal a confirmed blocker or claim an unverified fix.

1. Initial review: check applicable requirements and acceptance criteria, approach, material changed risk, obvious defects and the **producer → validator/enforcer → test → consumer/output** path; inspect bounded, file-scoped patches and relevant valid/invalid regressions. For recurring A/B/C/D/S2/S3 data production, the selected review card supplies stable review criteria; consult the standing execution issue only for a concrete question, not automatically every batch.
2. Follow-up: enumerate **every outstanding technical blocker** from previous reviews, compare the new HEAD to reviewed revisions, and independently check each root cause, complete fix, affected invariant and **shared** regression. An unresolved earlier `-1` must be checked before any new `+1`. **For A/B/C/D Candidate data PRs, re-review only candidates/Senses explicitly reported as blockers in prior review rounds, author rebuttals, and candidates actually added/changed/removed by fixes (including collateral deletion regressions). Do not discover or block on previously unchanged, unreported candidates—even if they match an earlier defect class.**
3. Expand scope only for a concrete doubt or blocker; avoid entire-diff rereads, unrelated history, full-file dumps, recurring scans or a sequence of duplicate findings. Verify that fixes address the shared cause, not only named examples.
4. **Never inspect, retrieve or wait for CI status/logs.** Pending, failed, missing or running CI must never delay a code-clean `+1`; incidentally visible CI must not affect the judgment. CI claims do not belong in Stage 1 evidence.
5. Submit `-1` for a confirmed blocker within the applicable review-round scope (cause, impact, safer fix, shared regression); otherwise submit substantive `+1` immediately and record non-blocking uncertainties. Final Stage 2 performs no independent technical review. **For a Candidate follow-up, resolving all previously raised blockers without a new fix regression requires `+1`; an unchanged candidate first noticed in that follow-up is not grounds to extend `-1`.** Code/contract PRs still require judgment of material new defects. `+1` asserts only that this focused code/fix gate passed, **not CI or merge readiness**. Never merge.

## 3. Stage 2 — final HEAD/CI gate and squash merge only

Stage 2 **exclusively owns CI status verification**: verify the PR/issue, unchanged current HEAD, effective substantive Stage 1 `+1` for that HEAD, absence of unresolved `-1` and a successful required GitHub Actions PR CI check on that exact HEAD. Consume Stage 1 PASS with Section 7's format tolerance; verify focused review evidence without repeating the technical audit. Do not require a comprehensive semantic audit or a second technical PASS. Do not classify changed files, choose CI tiers or reproduce workflow run/skip rules; `.github/workflows/ci.yml` determines required CI. An unrelated green check or check for another HEAD is insufficient.

Pending, failed, missing or stale required CI **blocks merge, not the technical `+1`**. Surface an actionable CI failure or missing gate and recheck its result later; a same-HEAD CI rerun does not require another Stage 1 review or replacement PASS. A correction that creates a new HEAD returns to Stage 1 for focused verification of that change and any unresolved blockers. An uncertain final gate or stale review marker also blocks merge. Route concrete contradictory technical evidence to Stage 1; CI state alone is not a technical `-1`.

If all gates hold, **squash-merge using the expected exact HEAD SHA**. Do not perform independent technical/semantic review, commission adversarial probes, require a second technical PASS or `+2`, issue GitHub APPROVE/REQUEST_CHANGES, or wait for post-merge master CI.

## 4. Select exactly one review prompt

For **technical Stage 1**: after reading this root file at the exact PR HEAD, determine the complete actual PR changed-path list (merge-base → HEAD), then load the applicable review card **from that same PR HEAD**, under `docs/review/prompts/`. Do not read all method cards or re-read the root file from `master` after already reading the reviewed HEAD. PR title is a routing hint **only when the actual changed files also match**.

- **Candidate-only A/B/C/D:** if all material changes are the selected method's `data/relation-candidates/<SSS>/<SSS>_<BB>_<method>_<model>.jsonl` production data, load `candidate.md` plus **exactly one** of `a.md`, `b.md`, `c.md`, `d.md` matching title and file. Do not load S2/S3 or generic code guides for a routine data batch.
- **S2 Admission-only:** `[S2/<model>]` Part PR with expected Relation/Drop data and no implementation changes → `s2.md`.
- **S3 Editorial-only:** `[S3/<model>]` shard PR with expected Relation/Drop data and no implementation changes → `s3.md`.
- **Other lexical/Canonical/STDICT data-only:** `data.md`.
- **Implementation, CI, schema, mixed or unclassified PR:** `code.md`. Open its **relevant specialist card(s) only when touched**: `search.md`, `toolchain.md`, `extension.md`, `licensing.md`, `data.md`.

The authoritative product contracts remain in `docs/relation-factory.md` and `docs/relation-editorial-policy.md`; standing A/B/C/D/S2/S3 **issues govern producer execution**, not recurring reviewer tool choreography. On a routine production-data PR, read the selected review card and submitted changed data; open an issue or affected product contract only for a concrete doubt or demonstrated failure. This routing does not relax any genuine technical blocker. Re-review follows Section 2's narrow boundary regardless of route.

**Final PR Stage 2** reads this root policy, effective current-HEAD `+1`, blocker history and required exact-HEAD GitHub Actions CI only; it does not open method cards or perform another technical/semantic audit.

## 5. Non-negotiable blocker discipline

**PR-body reporting is non-blocking (all methods and stages):** Method issues may prescribe a minimum execution summary, counts, sources or validation facts for authors to report, but **missing or incomplete PR-body fields, transcription mistakes and inconsistent summary numbers are never a `-1` by themselves**, even if the issue calls the summary mandatory or a public gate. Give a concise, non-blocking correction instruction in an otherwise technically passing `+1`; do not wait for a rewritten description, new commit or new HEAD to issue PASS. Conversely, a polished PR body does not prove the work was performed. If independent technical evidence establishes that a required sweep, source-sense verification, provenance boundary or output invariant was actually violated, issue `-1` for **that concrete production defect**, not for missing narrative evidence. Suspicion based only on absent PR-body details or inability to independently inspect private records is not proof of failure. Do not demand exhaustive private-ledger disclosure or per-lens accounting tables. On re-review, assess author explanations on their merits and close resolved technical objections promptly.

**Test and validator discipline:** Tests exist to protect product stability and established invariants, **not to maximize code coverage**. Review both the sufficiency **and necessity** of added checks. Before demanding a new validator/test or raising `-1` for missing coverage, demonstrate a plausible failure through a supported production path or an explicitly required security, licensing, or trust boundary; its material impact; and why existing checks do not suffice. Do not invent unreachable states solely to expose validator blind spots. Manually corrupting a correctly generated, read-only SQLite artifact is not, by itself, a production defect or grounds for a blocker—even if a generic provenance check could detect more mutations. Prefer the smallest shared protection, and weigh its implementation, recurring CI, maintenance, and review costs against actual regression-prevention value. Challenge redundant or artificial-only tests; do not demand them.

For a **shared defect**, demand a real failing example, correction at the common producer/validator/admission/consumer boundary, an **old-fails/new-passes shared regression** and enforcement for **all applicable existing records and future additions**. Reject example-only data patches and batch/word-specific regression memorization. Apply the review-round boundaries in Section 2: a shared-cause finding does not reopen unchanged, unreported Candidate targets on follow-up. Neither missing required validation nor false provenance/approval evidence can pass.

**Source-bound semantics and protected architecture:** Do not invent a mechanical test for subjective synonym/association merit. Apply the appropriate lexical/editorial and CI contract from the selected specialist card and current product policy only when relevant. A confirmed violation of source rights, identity, provenance or mandatory validation remains blocking; use the actual affected shared path rather than historical one-word tests.

## 6. Required exact-HEAD CI status

Stage 2 confirms that the **required GitHub Actions PR CI check completed successfully for the exact reviewed HEAD** before merging. The workflow alone decides which validations run or skip; reviewers do not maintain a second set of path, tier, schema or skip rules. A pending, failed, missing or stale check is not a merge pass. Stage 1 does not retrieve or use CI results in its technical judgment.

## 7. Technical GitHub PR review record (Stage 1)

Write **exactly one final GitHub PR Review COMMENT** per Stage 1 run (`gh pr review --comment`, **not** `gh pr comment`); never APPROVE/REQUEST_CHANGES. Verify HEAD again before submitting; never PASS an unreviewed new commit.

**Mandatory submission prefix:** line 1 is **exactly** `+1` or `-1`; line 2 is **exactly** `HEAD: <40-character lowercase hex SHA>`. No heading, bullet, code fence, whitespace or empty line before/between these lines. All prose/evidence follows line 2 (a blank line afterward is allowed). A review without substantive evidence is never sufficient.

**Stage 1 PASS consumption:** final Stage 2 may tolerate a malformed prefix **only if that same review unambiguously records `+1`, identifies the exact current 40-character HEAD somewhere and contains substantive evidence for the focused Stage 1 scope**. Do not block or demand resubmission solely for formatting or the technical reviewer having seen/mentioned CI; disregard those CI claims. Missing/contradictory evidence, ambiguous PASS or stale/wrong HEAD still fails. Producing reviewers must themselves use the **strict** prefix.

Record stage, issue/scope, approach/boundaries, actual reviewed evidence, confirmed blockers (or none), uncertainties/unrun checks and the SHA-bound conclusion, **without CI claims**. On initial `-1`, state confirmed targets, cause/impact, safer correction and required verification within the focused scope. On re-review, account for unresolved previous blockers, author replies, actual fix delta and direct regressions, including when HEAD is unchanged. Do not add unrelated comprehensive review or mandatory adversarial probes.
