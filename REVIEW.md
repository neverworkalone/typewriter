# Typewriter PR Review

This root `REVIEW.md` is the **authoritative gate policy**. Read it from the **latest PR HEAD** before every review; never read `AGENTS.md`, personal/global `MEMORY.md`, agent memories or implementation instructions while reviewing. Review the reported problem **and the validity of the approach**. Use the smallest sufficient evidence; correctness outranks speed.

## 1. Enter and select exactly one stage

1. Identify the current 40-hex PR HEAD, base, linked issue/acceptance criteria and owner decisions, **complete changed-path list**, earlier review markers/SHAs and unresolved blockers. Read this root file **at that HEAD**.
2. **Stage 1:** no currently effective same-HEAD `+1` (including when a later `-1` reopens the gate); conduct a focused first review or verify **all** still-relevant earlier Stage 1/2 blockers on the current HEAD, even without a new commit. **Stages 1 and 2 run independently of CI; Stage 3 alone validates CI before merging.**
3. **Stage 2:** recognizable, substantive currently effective same-HEAD Stage 1 PASS, but no effective subsequent `+2`; form a separate full technical judgment, then examine Stage 1 evidence. CI is outside Stage 2's review gate.
4. **Stage 3:** sequential independent, evidence-bearing same-HEAD `+1` and `+2`, the appropriate successful exact-HEAD CI gate and no unresolved blocker; verify every final gate and merge only when all pass.

A new commit makes earlier PASS markers **stale**, not previously verified reasoning: Stage 1 must review the new HEAD before Stage 2. Bare markers or evidence-free reviews do not count. The same GitHub account may perform stages only in **separate runs/contexts**; never submit `+1` and `+2` together.

PR descriptions and issue progress comments are not authoritative review evidence; the latest HEAD's code and artifacts are. **Missing, incomplete, inconsistent or outdated PR-body information is non-blocking feedback, even if the linked method issue specifies a required PR summary.** Never submit or retain `-1`, withhold a technical `+1`/`+2`, or demand a dummy commit **solely** for a PR description correction; record the focused correction as a non-blocking instruction and issue the technically warranted PASS. A real, independently demonstrated failure of required production, provenance, validation or output remains a blocker; the missing description is not evidence that the work was omitted.

**Author-response obligation on every re-review:** regardless of whether the trigger is a new HEAD or a new comment, inspect relevant PR conversation comments and inline review-thread replies from the author since the preceding review. Evaluate every substantive correction, explanation or rebuttal to an earlier blocker against the current HEAD's code/artifacts and owner decisions; comments are arguments to verify, not authoritative technical evidence. Explicitly accept or rebut each disputed blocker with reasons. If the prior `-1` was mistaken or the blocker is resolved, replace that judgment with a new evidence-bearing PASS (`+1` or `+2` at the appropriate stage), **even on an unchanged HEAD**; never require a dummy code change. If retaining `-1`, address the author's actual counterargument and identify the concrete remaining failure rather than repeating the previous claim. Stage 2 must preserve its independent assessment: form its own technical judgment before examining Stage 1's conclusions and the related discussion.

**Converge rather than repeat:** reviewer and author are collaborators seeking the correct outcome, not opponents defending earlier positions. On each exchange, acknowledge verified points, narrow remaining disagreements to concrete requirements or evidence, and identify the next actionable resolution. Reconsider partially valid objections and adjust the proposed fix or verdict accordingly. Do not restate an answered claim without new evidence or a specific explanation of why the reply fails. If discussion makes no substantive progress, summarize agreed facts, disputed evidence, remaining risks and the decision needed, then escalate to the owner rather than cycling indefinitely. Escalation never authorizes PASS while a confirmed blocker remains; there is no arbitrary limit on productive exchanges.

## 2. Stage 1 — quick independent code/fix review

**Aim for 1–3 minutes on routine PRs, not a deadline.** Do not duplicate the exhaustive Stage 2 assessment, conceal a confirmed blocker or claim an unverified fix.

1. Initial review: check the issue, approach, material changed risk, obvious defects and the **producer → validator/enforcer → test → consumer/output** path; inspect bounded, file-scoped patches and relevant valid/invalid regressions.
2. Follow-up: enumerate **every outstanding previous Stage 1 and Stage 2 blocker**, compare the new HEAD to reviewed revisions, and independently check each root cause, complete fix, affected invariant and **shared** regression. A previous Stage 2 `-1` must be checked here before any new `+1`.
3. Expand scope only for a concrete doubt or blocker; avoid entire-diff rereads, unrelated history, full-file dumps, recurring scans or a sequence of duplicate findings. Verify that fixes address the shared cause, not only named examples.
4. **Never inspect, retrieve or wait for CI status/logs.** Pending, failed, missing or running CI must never delay a code-clean `+1`; incidentally visible CI must not affect the judgment. CI claims do not belong in Stage 1 evidence.
5. Submit `-1` for any confirmed new or unfixed earlier blocker (cause, impact, safer fix, shared regression); otherwise submit substantive `+1` immediately and flag uncertain risks for Stage 2. `+1` asserts only that this focused code/fix gate passed, **not CI or merge readiness**. Never merge.

**Stage 1 Candidate form gate (all A/B/C/D, including 500-record factory batches):** Candidate PRs are not judged solely by Candidate v1 shape, source-sense matching, or whether `candidates: []` is permitted. **Preserve intelligible individual WORDS and concise meaning-extending SCENE/IMAGE/SENSORY/EMOTION/ACTION PHRASES; strictly reject mechanical gloss copies, disguised clauses and SENTENCES.** This is a *Stage 1 output eligibility check*, **not** Stage 2's relation-worth/Tier/Drop selection.

- **Independent words:** preserve a source-sense-bound, intelligible path even if it is weak, ordinary, creative, cross-POS, or unfamiliar. Do not require a direct synonym or a minimum frequency. A word is not junk just because it is context-dependent.
- **Words containing the source lemma:** flag for **case-by-case semantic and lexical review**, **not automatic rejection**. Check whether the compound/derived form names a genuinely different word, role, object or association (`건축 → 건축가` can pass) versus a self-recommendation or inflectional/orthographic decoration. Exact lemma and lemma plus only a trailing annotation (`공탁 → 공탁(供托)`) are prohibited by the shared Candidate contract; **containing the lemma is not itself a blocker**.
- **Multiword lexical expressions, short phrases, idioms, and concatenated/source-lemma-containing expressions:** the strict check targets **mechanical gloss restatements, unspaced ordinary syntactic fragments, arbitrary modifier+lemma expansions and disguised narration**, **not** artistic merit or phrase count. Preserve compact sense-bound expansions into a scene, image, sensation, action or emotion even when the wording is ordinary (`수괘` [frost] → `겨울 아침`, `산뜩` → `가슴 철렁`). Reject a plain gloss attribute+category (`가는소금` → `하얀 소금`, `가는솜방망이` → `노란 꽃`) or modified lemma (`걸음걸이` → `느린 걸음걸이`) that merely repeats the source without a different association. Whitespace or concatenation alone neither qualifies nor disqualifies a phrase. **Do not demand unusual originality, demonstrably superior imagery, or Stage 2 admission value in Stage 1.** A genuinely debatable compact expression stays for Stage 2 rather than causing repeated `-1`.
- **Complete sentences, predicative clauses, narratives of a particular action/event/procedure, and sentence fragments masquerading as nominal phrases are strictly forbidden in final `candidates[]` (zero exceptions)**. E.g. `검지기 → 누전이 되면 경보가 울린다`, `격벽 → 격벽을 여는 데 에너지가 필요하다`, `겅중 → 긴 다리로 뜀`. Removing punctuation, changing endings, or appending `scene/process/thing` does not make a narrated event eligible. An independent verb lemma such as `떨다` remains an allowed **word**, not an event description.
- **Risk-first review protocol:** read the *full changed-path list*, then target **(1) sentence/verb-phrase patterns, (2) lemma-containing words and phrases, (3) multiword gloss-like/collocational expressions, (4) ordinary standalone words as positive controls** against actual Canonical lemma and bound sense. Search/inspect enough changed candidates across the affected batch to establish whether a defect is systemic; do not pretend a small sample or a schema-only CI pass is a census. **Any confirmed forbidden sentence or self-repetition is a `-1`; demonstrable repeated mechanical gloss restatements or disguised clauses are also production-form `-1`, consolidated by defect class, but ordinary scene/image associations are not blockers merely for being conventional**, not one comment per word. If a single questionable expression is genuinely debatable, identify it for Stage 2 instead of imposing a blanket subjective cutoff. Fix the general producer/checking rule for future batches rather than requesting only example-word substitutions.

**Candidate preservation and deletion-diff audit on blocker fixes (all A/B/C/D):** Removing a forbidden candidate can resolve a blocker; **removing an eligible independent word as collateral damage is a separate Stage 1 regression**. Evaluate both the corrected output and what disappeared.

- **Track the entire fix, not just the last commit:** on Candidate re-review, compare the last substantively reviewed pre-fix candidate snapshot (and the initial pre-fix snapshot when fixes span multiple commits) with the current HEAD by `(record_id, sense_id, candidate)`. Enumerate and count removed, added and replaced candidates; inspect the **negative diff** as well as surviving strings. A clean Candidate v1 validator or an author's "fully rechecked" claim does not establish that deleted candidates were ineligible.
- **Require source-bound reasons, preserve legitimate discoveries:** the author should report the removal count, actual defect classes and relevant positive controls, grouping explanations rather than writing one comment per word. A removal needs evidence that the candidate violates **Stage 1 output eligibility** (e.g. a disguised clause, routine gloss fragment, exact self-repetition or an unmistakably wrong source sense). **Not appearing as a Canonical headword/search form, being present in a gloss, unfamiliarity, different POS, weak/indirect association or low anticipated Tier is not by itself a reason to delete an independent word or compact meaning-extending scene/image/sensory expression**. Do not purge by blanket dictionary membership, gloss-token, suffix, substring or "metadata word" filters; assess the actual lexical item and bound sense. 
- **Independently verify deletions:** group the removed set by the claimed failure mechanism, inspect the removed candidates against their exact Canonical source senses, and challenge overly broad groups with **valid standalone-word and concise scene/sensory-expression positive controls** as well as truly invalid gloss paraphrases. Expand inspection to affected removals when a broad filter is demonstrated; do not mistake sampling for exhaustive verification. If an eligible word or compact meaning-extending expression was removed without a concrete Stage 1 eligibility failure, require restoration or a substantiated correction and retain `-1` until resolved. Genuine Stage 1-ineligible strings should stay removed. **Stage 2, not Stage 1, determines the eventual relation admission/Tier of preserved words.**

This focused form gate is **separate from the lenient Stage 1 treatment of weak but intelligible word relations** and from Stage 2's independent admission/editorial judgment. Do **not** add a brittle universal regex/sub-string/word-count blocker or require all words to appear literally in a gloss.

## 3. Stage 2 — independent comprehensive technical gate

Stage 2 owns the **entire material approach and affected risk surface**, previous blocker closure and at least one adversarial challenge; it does not inspect CI or merge.

1. Confirm the same-HEAD Stage 1 PASS **marker/identity only** without first reading its conclusions. Independently inspect the requirement, approach, complete material diff/risk, producer/consumer paths, source and provenance boundaries, canonical/search fidelity, failure/valid paths, regressions and test adequacy. A clean Stage 1 does **not** narrow this scope.
2. Recheck all relevant Stage 1/2 blockers and fixes. **After forming your own technical judgment**, read Stage 1's substantive review and challenge its coverage, reasoning, regressions and verification of previous Stage 2 blockers. Do **not** inspect or penalize Stage 1's CI-tool usage or awareness; disregard its CI claims entirely.
3. **Never inspect, retrieve or wait for CI status, checks, workflow runs or logs.** Pending, missing, failed, stale or running CI must **never** delay or change a code-clean `+2`; incidentally visible CI is irrelevant. Assess the changed CI/validator/test *source and contracts* as part of the technical review, but leave CI execution evidence exclusively to Stage 3.
4. Perform **at least one production-grounded targeted adversarial probe** (requirement → producer → shared validator/consumer → known-invalid case), checking positive/negative behavior, applicable existing/future records and test registration. The invalid case must model a plausible supported-path failure or an explicitly required trust/security boundary; arbitrary post-build mutation of a correctly generated read-only artifact does not qualify on its own. A probe need not discover a blocker. One representative probe is the **minimum**, never proof that an entire defect class was audited.
5. **When a concrete systemic defect is demonstrated:** establish root cause and **demonstrably affected population** (matching records, relevant same-source peers, prior reverse links and shared production paths); inspect actual source and **bound target sense/contract**, plus plausible usage contexts and positive/negative controls. For `direct`/`antonym`, a blocker must explain why no natural, recurring context supports the claimed similarity/opposition. A short gloss mismatch, non-exclusive definitions, possible co-existence or lack of universal substitution alone does not demonstrate an error. A plausible contextual reading may support the relation even when a strict gloss-only interpretation would not. A merely topical or contrastive creative association, or a minor relevance difference, is **not** evidence of a dictionary-relation defect. Consolidate genuine class-level findings with a safer fix and shared regression.
6. **On re-review of that demonstrated systemic defect:** independently verify the **identified affected class and resulting changes**, not only earlier examples or a producer's “all checked” assertion. Identify any unverified remainder. Scope work to demonstrated risk, **not a subjective near/association census or automatic repository-wide exhaustive audit on routine PRs**.
7. Submit substantive `+2` as soon as independent technical review, earlier blocker fixes, Stage 1's technical evidence and adversarial/scope validation pass, **regardless of CI state**. Submit `-1` only for a confirmed technical blocker, with cause, impact, safer shared fix and verification; pending or failed CI alone is **not** a Stage 2 `-1`. A Stage 2 `-1` returns to Stage 1 after the fix/new HEAD. `+2` certifies the technical gate only, **not CI or merge readiness**. Never merge or demand GitHub APPROVE.

**Candidate fixes at Stage 2:** Independently challenge the producer's and Stage 1 reviewer's deletion-diff conclusions, including whether broad cleanup discarded valid, source-sense-bound standalone words or compact scene/image/sensory associations. Check the pre-fix → current-HEAD negative diff and confirmed positive controls; an apparently clean final Candidate file does not by itself prove preservation.

## 4. Stage 3 — final gate and squash merge only

Stage 3 **exclusively owns CI verification**: verify the current PR/issue and **unchanged HEAD**, sequential independent evidence-bearing Stage 1 `+1` and Stage 2 `+2` for that HEAD, the correct successful **exact-HEAD** CI/skip gate under Section 7 and `docs/review-toolchain.md`, and no later unresolved `-1` or contradictory evidence. Consume Stage 1 PASS with Section 8's tolerance. Classify the complete changed-path list and validate the actual required tier/skip evidence; an unrelated green check is insufficient. If CI is pending, **do not merge**; recheck the CI gate when it is evaluated again, without asking Stage 2 to rerun or reissue `+2`. Failed, missing, stale or invalid CI/skip evidence **blocks merge**, not the technical `+2`; surface an actionable CI failure for correction, with a new HEAD requiring fresh Stage 1 and Stage 2 passes. An uncertain gate or stale review marker also blocks merge; route genuine technical blockers to the appropriate earlier stage.

If all gates hold, **squash-merge using the expected exact HEAD SHA**. No new deep technical review, adversarial probe, `+3`, GitHub APPROVE/REQUEST_CHANGES or post-merge master CI requirement.

## 5. Risk routing — load relevant guides, not every guide

- Lexical data, schema, senses, relations, editorial QA, canonical/admission: **read `docs/review-data.md`** and apply **`docs/relation-editorial-policy.md` as the current owner decision**. `direct`/`antonym` require source-bound semantic similarity/opposition, which may be established by a plausible, recurring natural use context; do not require exhaustive gloss equivalence, universal sentence substitutability or logical exclusivity. A reviewer should state the plausible context before deciding a material mismatch remains. Writer-facing `near`/`mood`/`scene`/`sensory`/`action`/`association` are **preserve-first**, judged primarily on same-source/group relevance 1–9, not strict substitutability.
- **Issue #838 말의 결/연상:** `docs/relation-editorial-policy.md` ("Scope of Issue #838") and `docs/review-data.md` define the contract; this file does not require reading any other instruction file. Review the actual relations and Tiers (연상 Tier 1 = informal-synonym-candidate level, relative within the same source/group, no quotas) normally. ID targets must bind the exact headword/homograph/sense; text-only targets must be non-clickable with no reverse and no invented ID; authored ID↔ID relations are explorable both ways with per-direction Tier. Text-only and bidirectional behaviour are contracts to verify **once the code implementing them exists**; do not fail a PR for them before that, and do not accept data that relies on them without it. `data/headword-candidates/pr-<PR number>.jsonl` is checked only for JSONL/Schema v1 conformance, a real `source_record_id`/`source_lemma`, and obvious junk or a candidate whose same meaning is obviously already an existing headword (same `term` with a different `meaning_hint` is a distinct valid candidate; never reject by spelling alone); promotion merit and deep candidate QA are not `-1` grounds.
- Search, ranking, normalization, candidate eligibility and ordering: **read `docs/review-search.md`**.
- CI, validators, factory/build, SQLite, generated artifacts and test policy: **read `docs/review-toolchain.md`**.
- Extension, UI, Chrome APIs, MV3, storage and WASM: **read `docs/review-extension.md`** when touched.
- External sources, provenance, licensing or distribution: **read `docs/review-licensing.md`** when touched.

For a data pipeline touching multiple boundaries, trace **candidate → source-bound semantic QA → admission → canonical → direct search** and load each relevant guide. Keep current and historical evidence distinct; do not let producer self-check masquerade as independent/human QA. Apply existing owner decisions, but never infer third-party redistribution rights from public R&D visibility.

## 6. Non-negotiable blocker discipline

**Corpus-backed C/D Candidate reviews — execution vs. reporting:** C's owner-approved #1155 procedure (and D's #1156) governs actual production: correct source-sense VERIFIED contexts, required independent exploration, truthful local evidence, and eligible Candidate v1 outputs are substantive requirements. A **demonstrated** omitted exploration pass, false VERIFIED attribution, wrong-sense candidate, fabricated execution evidence, invalid output, or systematic improper candidate deletion is a technical `-1` with a concrete affected case or supported failure mechanism. The producer's PR summary is not itself independent proof of private corpus inspection; do not substitute a perfectly balanced table for source-bound quality review.

**PR-body reporting is non-blocking (all methods and stages):** Method issues may prescribe a minimum execution summary, counts, sources or validation facts for authors to report, but **missing or incomplete PR-body fields, transcription mistakes and inconsistent summary numbers are never a `-1` by themselves**, even if the issue calls the summary mandatory or a public gate. Give a concise, non-blocking correction instruction in an otherwise technically passing `+1`/`+2`; do not wait for a rewritten description, new commit or new HEAD to issue PASS. Conversely, a polished PR body does not prove the work was performed. If independent technical evidence establishes that a required sweep, source-sense verification, provenance boundary or output invariant was actually violated, issue `-1` for **that concrete production defect**, not for missing narrative evidence. Suspicion based only on absent PR-body details or inability to independently inspect private records is not proof of failure. Do not demand exhaustive private-ledger disclosure or per-lens accounting tables. On re-review, assess author explanations on their merits and close resolved technical objections promptly.

**Test and validator discipline:** Tests exist to protect product stability and established invariants, **not to maximize code coverage**. Review both the sufficiency **and necessity** of added checks. Before demanding a new validator/test or raising `-1` for missing coverage, demonstrate a plausible failure through a supported production path or an explicitly required security, licensing, or trust boundary; its material impact; and why existing checks do not suffice. Do not invent unreachable states solely to expose validator blind spots. Manually corrupting a correctly generated, read-only SQLite artifact is not, by itself, a production defect or grounds for a blocker—even if a generic provenance check could detect more mutations. Prefer the smallest shared protection, and weigh its implementation, recurring CI, maintenance, and review costs against actual regression-prevention value. Challenge redundant or artificial-only tests; do not demand them.

For a **shared defect**, demand a real failing example, correction at the common producer/validator/admission/consumer boundary, an **old-fails/new-passes shared regression** and enforcement for **all applicable existing records and future additions**. Reject example-only data patches and batch/word-specific regression memorization. Neither missing required validation nor false provenance/approval evidence can pass.

**Subjective lexical correctness is source-bound editorial judgment**, not an excuse to introduce blanket mechanical synonym validators; a valid entry with zero relations must remain eligible. For `direct`/`antonym`, assess the bound meanings and a plausible recurring usage context: meaningful similarity/opposition can survive different gloss emphasis, non-universal substitutability, or coexisting qualities. Before `-1`, explain why no plausible natural context supports the actual relation; topic-only, co-occurrence, causation and a contrastive scene alone are insufficient. The owner-approved comfort/discomfort, culinary sour/sweet, literary realism/hallucination, 차분하다/침착하다 and 늪/습지 calibrations are documented in `docs/relation-editorial-policy.md`. For exploratory relations, prioritize an intelligible creative path and compare **relevance against existing and proposed peers of the same source sense/UI group**; downrank marginal ideas instead of vetoing them. A subjective category preference or 4-vs-5 band difference is not a `-1`; demand a demonstrated material error or significant, evidenced rank inversion. Respect fail-closed holds/admission and source rights. For CI/canonical architecture changes, preserve one complete-revision context, the global semantic audit before SQLite, shared downstream reuse and the **exact-current-revision one-build invariant**; see the mandatory counters/guards in `docs/review-toolchain.md`.

## 7. Required exact-HEAD CI

- **Docs-only:** every path in `docs/**`, `README.md` or `REVIEW.md` → successful workflow check explicitly reporting the `ci:normal` skip. Any mixed/renamed/unclassifiable path must **not** get this skip.
- **All non-docs PRs:** successful exact-HEAD `ci:normal` with its complete-revision/SQLite gate. There is no candidate-only route. A registered Deep dependency adds only its affected exact-HEAD Deep checks after Normal; CI-selection changes and unclassifiable paths take Normal, plus any independently matched affected Deep checks; Full Deep is weekly/manual only. `ci:fast` is an internal Normal checkpoint; Normal may not duplicate its audit or SQLite build.
- **New path / missing check:** use the repository's general extension rule in `docs/review-toolchain.md`: an unresolved path remains fail-closed; a verified append-only binding to an existing always-on Normal regression requires Normal only, while affected Deep dependencies require the selected Deep checks. When a contract lacks coverage, demand a shared regression and its real registry/dependency wiring; do not accept an unrelated `ci:all` pass as a substitute for fixing recurrent classification omissions. New registration may not remove or override existing Deep triggers. Check exact-HEAD proof in Stage 3 only.
- **Deep:** use the tier ownership and exact-head triggers in `docs/review-toolchain.md`. A Deep-owned implementation/contract change requires successful **exact-HEAD evidence for each affected Deep check**; scheduled or skipped evidence cannot satisfy that gate. The existing `Validate and test Typewriter` PR check runs Normal plus the selected checks through `ci:pr`. CI runner/registry/workflow/classifier changes and unknown or unclassifiable paths retain Normal and diagnostics, with matched affected Deep checks only. Full `ci:all` is not a PR gate; it runs weekly or manually. Registry `dependency_paths` select affected checks; `deep_input_paths` describe their data inputs and do not alone trigger every Deep check. Routine schema-valid Canonical and relation changes use Normal and their shared validators. One-off checks are run for the task that needs them and are not retained as Manual tests without a current recurring workflow.

**Stage 3 alone validates actual changed paths and successful exact-HEAD workflow/skip evidence**, not only a green badge; inspect passed CI logs when workflows/validators/fixtures/expected behavior change or code contradicts claimed coverage. Never claim unrun native, corpus or manual checks passed. **Stages 1 and 2 must not inspect, retrieve or wait for CI status/logs.** No post-merge `master` `ci:normal` is required.

## 8. Strict GitHub PR review record (Stages 1 and 2)

Write **exactly one final GitHub PR Review COMMENT** per run (`gh pr review --comment`, **not** `gh pr comment`); never APPROVE/REQUEST_CHANGES. Verify HEAD again before submitting; never PASS an unreviewed new commit.

**Mandatory submission prefix:** line 1 is **exactly** `+1`, `+2`, or `-1`; line 2 is **exactly** `HEAD: <40-character lowercase hex SHA>`. No heading, bullet, code fence, whitespace or empty line before/between these lines. All prose/evidence follows line 2 (a blank line afterward is allowed). A review without substantive evidence is never sufficient.

**Asymmetric Stage 1 PASS consumption:** Stage 2/3 must accept a malformed Stage 1 prefix **only if the same review unambiguously records PASS/`+1`, identifies the exact current 40-character HEAD somewhere, and contains substantive Stage 1 code/fix evidence**. Do not block or demand resubmission solely for formatting or Stage 1 having seen/mentioned CI; disregard those CI claims. Missing/contradictory evidence, ambiguous PASS or stale/wrong HEAD still fails. Producing reviewers (including Stage 2) must themselves use the **strict** prefix.

Both stages record stage, issue/scope, approach/boundaries, actual reviewed evidence, confirmed blockers (or none), uncertainties/unrun checks and SHA-bound conclusion. On `-1`, explain root cause/impact, safer correction and required regression. On re-review, identify relevant author replies since the previous review and explain which earlier blockers were accepted, withdrawn, or maintained and why, including when HEAD is unchanged. Stage 1 briefly accounts for **all** prior Stage 1/2 blockers on follow-up; Stage 2 records its independent full technical judgment, substantive Stage 1 critique, adversarial probe and regression adequacy **without CI claims**.
