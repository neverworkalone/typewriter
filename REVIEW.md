# Typewriter PR Review

This root `REVIEW.md` is the **authoritative gate policy**. Read it from the **latest PR HEAD** before every review; never read `AGENTS.md`, personal/global `MEMORY.md`, agent memories or implementation instructions while reviewing. Review the reported problem **and the validity of the approach**. Use the smallest sufficient evidence; required correctness is non-negotiable, **but speculative safeguards must not override recurring production speed and AI token efficiency**.

## Production efficiency review

**For repeated production, speed and AI token cost are first-class review criteria.** Reject unnecessary checks, receipts, per-item CLI calls, and repeated reads/hashes/writes unless they prevent a demonstrated defect. Preserve required semantic quality and existing final validation/CI. Judge optimizations against the **previous working path** using actual production time and tokens; more safeguards alone are not an improvement.

## 1. Enter and select exactly one stage

1. Identify the current 40-hex PR HEAD, base, linked issue/acceptance criteria and owner decisions, **complete changed-path list**, earlier review markers/SHAs and unresolved blockers. Read this root file **at that HEAD**.
2. **Stage 1 — consolidated technical/data review:** no currently effective, substantive same-HEAD technical PASS (including when a later `-1` reopens the gate); conduct the initial review or verify all still-relevant earlier blockers and actual fix changes. One reviewer, independent of the producer, owns requirements, approach, correctness, material risk and regression adequacy. Return `+1` or `-1`; do not inspect CI or merge.
3. **Stage 2 — final gate and squash merge:** an effective same-HEAD technical PASS exists; verify its evidence, the current HEAD, no unresolved blocker and required exact-HEAD CI, then merge only when every final gate passes. Pending CI keeps the PR at this gate; it does not restart technical review.

A new commit makes earlier PASS markers **stale**, not previously verified reasoning: Stage 1 verifies the new HEAD using the focused follow-up scope in Section 2. Bare markers or evidence-free reviews do not count. The same GitHub account may perform the two stages only in **separate runs/contexts**. Stage 2 is not another technical assessment; do not simulate two technical reviewers or require a new `+2`.

**Scope and transition:** These PR roles are separate from **Relation Factory production Stages 1/2/3**, which remain unchanged. This file owns PR review roles and verdicts even when a standing issue still names the former second reviewer, `+2` or three-stage PR flow. Retain earlier review evidence, author responses and unresolved blockers. A former focused `+1` alone does not establish the consolidated technical PASS: close only any unverified material scope, reusing verified work and respecting the Candidate follow-up boundary below. An effective, substantive same-HEAD comprehensive `+2` from the former policy may satisfy the technical gate; do not demand a replacement marker or dummy commit solely for this transition.

**PR changed-path and deletion evidence (all stages):** Determine actual PR scope from GitHub's **complete PR changed-file list** or a **merge-base → PR HEAD** diff, such as `git diff --name-status <base>...<HEAD>` (three dots) or `git diff --name-status "$(git merge-base <base> <HEAD>)" <HEAD>`. Do **not** infer that a PR deleted or modified an artifact merely because it is present on a newer base/`master` but absent on a branch forked earlier; a two-endpoint `git diff <base> <HEAD>` or raw branch file comparison can incorrectly report such **base-only additions** as deletions. Before marking `-1` for deleted Candidate JSONL or other missing files, confirm the path is **actually marked deleted in the PR diff**, check the merge base and exact reviewed HEAD, and establish the real impact. If diff sources disagree, resolve the ref/merge-base discrepancy instead of escalating an unverified absence to a blocker. On re-review, compare old reviewed HEAD → new HEAD separately for fix regressions; that incremental comparison does **not** replace the merge-base-based PR scope.


PR descriptions and issue progress comments are not authoritative review evidence; the latest HEAD's code and artifacts are. **Missing, incomplete, inconsistent or outdated PR-body information is non-blocking feedback, even if the linked method issue specifies a required PR summary.** Never submit or retain `-1`, withhold a technical `+1`, or demand a dummy commit **solely** for a PR description correction; record the focused correction as a non-blocking instruction and issue the technically warranted PASS. A real, independently demonstrated failure of required production, provenance, validation or output remains a blocker; the missing description is not evidence that the work was omitted.

**Author-response obligation on every re-review:** regardless of whether the trigger is a new HEAD or a new comment, inspect relevant PR conversation comments and inline review-thread replies from the author since the preceding review. Evaluate every substantive correction, explanation or rebuttal to an earlier blocker against the current HEAD's code/artifacts and owner decisions; comments are arguments to verify, not authoritative technical evidence. Explicitly accept or rebut each disputed blocker with reasons. If the prior `-1` was mistaken or the blocker is resolved, replace that judgment with a new evidence-bearing technical `+1`, **even on an unchanged HEAD**; never require a dummy code change. If retaining `-1`, address the author's actual counterargument and identify the concrete remaining failure rather than repeating the previous claim.

**Converge rather than repeat:** reviewer and author are collaborators seeking the correct outcome, not opponents defending earlier positions. On each exchange, acknowledge verified points, narrow remaining disagreements to concrete requirements or evidence, and identify the next actionable resolution. Reconsider partially valid objections and adjust the proposed fix or verdict accordingly. Do not restate an answered claim without new evidence or a specific explanation of why the reply fails. If discussion makes no substantive progress, summarize agreed facts, disputed evidence, remaining risks and the decision needed, then escalate to the owner rather than cycling indefinitely. Escalation never authorizes PASS while a confirmed blocker remains; there is no arbitrary limit on productive exchanges.

## 2. Stage 1 — consolidated technical/data review

**Aim for 1–3 minutes on routine PRs, not a deadline.** Cover the former focused and comprehensive technical responsibilities in **one pass**, not two checklists in sequence. Preserve required quality; spend additional time only on material scope, concrete uncertainty or confirmed defects.

1. **Initial review — broad once:** inspect the requirements, approach, complete material changed scope and the actual **producer → validator/enforcer → test → consumer/output** paths, including relevant source/provenance boundaries and valid/invalid behavior. Use bounded file-scoped patches, inexpensive whole-scope diagnostics and risk-first inspection instead of exhaustive item-by-item rereads. **Do not stop at the first blocker:** finish the material risk sweep, investigate demonstrated defect classes and consolidate confirmed targets, cause/impact and closure conditions in the first `-1`.
2. **Use the smallest sufficient verification:** reuse relevant existing evidence and checks. There is **no minimum adversarial-probe, finding or new-test count**. Add or run a targeted check only to resolve a concrete uncertainty or demonstrate a plausible failure through a supported production path or an explicitly required trust/security boundary. Do not invent unreachable states or hypothetical production scenarios to manufacture blockers, or demand redundant safeguards once required criteria are satisfied.
3. **Routine Candidate-only batches — keep production moving:** perform the initial required whole-batch checks once, including the independent normalized containment check below; reuse applicable existing schema/validation evidence. Inspect form and bound source Sense in risk-first groups. Do not re-audit unchanged producer, validator, build or SQLite implementations on every batch, run a second blanket semantic pass, or demand full pipeline reruns, per-item receipts, private ledgers or a full test suite merely for extra confidence. A demonstrated production defect may require a bounded investigation of its shared cause.
4. **Follow-up — narrow and deep:** account for **every unresolved earlier technical blocker**, including those raised under the former Stage 1/2 policy; assess author responses, the last reviewed HEAD → current HEAD changes, root-cause closure and direct regressions/side effects in affected invariants, shared paths and consumers. Carry forward verified unchanged work. A new HEAD **does not restart broad discovery**. Assess newly introduced material changes, but do not search unrelated unchanged areas or reopen the initial whole-PR sweep. For A/B/C/D Candidate data, the explicit target/fix-delta boundary below governs even when an earlier finding described a shared defect class.
5. **Concrete failures encountered during follow-up:** a confirmed material code/contract failure encountered while checking an existing blocker or an actual fix path remains blocking. Identify that connection and the affected population; if it existed at the initial HEAD, acknowledge the initial coverage miss and improve the smallest relevant initial check for future work. This does **not** authorize unrelated discovery or a new `-1` for an unchanged, previously unreported Candidate word/Sense. Verify shared causes within the applicable review-round scope, not only example substitutions.
6. **Never inspect, retrieve or wait for CI status, checks, workflow runs or logs.** Pending, failed, missing, stale or running CI must never delay a technically clean `+1`; incidentally visible CI must not affect the judgment. Assess changed CI/validator/test **source and contracts** when relevant, but leave CI execution evidence exclusively to Stage 2. CI claims do not belong in Stage 1 evidence.
7. Submit `-1` only for a confirmed technical blocker within the applicable review-round scope, with concrete targets, cause, impact, safer correction and required verification. Otherwise, once applicable required checks and criteria are satisfied, submit substantive `+1` **immediately**; record non-blocking uncertainty without commissioning another technical pass. **For Candidate follow-ups, resolution of all reported blockers with no new fix regression requires `+1`.** This PASS covers the consolidated technical gate, **not CI or merge readiness**. Never merge.

**Stage 1 Candidate form gate (all A/B/C/D, including 500-record factory batches):** Candidate PRs are not judged solely by Candidate v1 shape, source-sense matching, or whether `candidates: []` is permitted. **Preserve intelligible individual WORDS and concise meaning-extending SCENE/IMAGE/SENSORY/EMOTION/ACTION PHRASES; strictly reject mechanical gloss copies, disguised clauses and SENTENCES.** This is a *Stage 1 output eligibility check*, **not** Relation Factory Stage 2's relation-worth/Tier/Drop selection.

- **Independent words:** preserve a source-sense-bound, intelligible path even if it is weak, ordinary, creative, cross-POS, or unfamiliar. Do not require a direct synonym or a minimum frequency. A word is not junk just because it is context-dependent.
- **Source lemma ↔ candidate containment (mandatory zero):** If either side contains the other after the defined whitespace/hyphen normalization, **reject the candidate without exceptions**, even when it is a separately attested word, an independent concept or a potentially useful image. Examples: `건축 → 건축가`, `반송 → 반송파`, `눈 → 눈빛`, `불 → 불씨`, `꽃 → 꽃말`, `개 → 개집`. This rule is distinct from shared-stem/suffix/part-of-speech similarities **without actual containment**, which still need source-Sense judgment. Exact source lemma and annotation-only repeats remain forbidden.
- **Clearly trivial morphology/derivation:** the producer and initial Candidate reviewer reject `깜빡대다 → 깜빡이다` (simple form/ending variant), `조퇴하다 → 조퇴` (same-concept nominalization), `팔딱하다 → 팔딱팔딱` (unhelpful repetition), as well as `건축 → 건축가` above. These are narrow Stage 1 eligibility examples, **not** a spelling/regex rule against all related stems, word classes or repeated syllables. Debatable indirect connections such as `어정대다 → 낙타` stay eligible for Relation Factory Stage 2 to judge.
- **Multiword lexical expressions, short phrases, idioms, and concatenated expressions without forbidden source-lemma containment:** the strict check targets **mechanical gloss restatements, unspaced ordinary syntactic fragments, arbitrary modifier+lemma expansions and disguised narration**, **not** artistic merit or phrase count. Preserve compact sense-bound expansions into a scene, image, sensation, action or emotion even when the wording is ordinary (`수괘` [frost] → `겨울 아침`, `산뜩` → `가슴 철렁`). Reject a plain gloss attribute+category (`가는소금` → `하얀 소금`, `가는솜방망이` → `노란 꽃`) or modified lemma (`걸음걸이` → `느린 걸음걸이`) that merely repeats the source without a different association. Whitespace or concatenation alone neither qualifies nor disqualifies a phrase. **Do not demand unusual originality, demonstrably superior imagery, or Relation Factory Stage 2 admission value in Candidate production/review.** A genuinely debatable compact expression stays for Relation Factory Stage 2 rather than causing repeated `-1`.
- **Complete sentences, predicative clauses, narratives of a particular action/event/procedure, and sentence fragments masquerading as nominal phrases are strictly forbidden in final `candidates[]` (zero exceptions)**. E.g. `검지기 → 누전이 되면 경보가 울린다`, `격벽 → 격벽을 여는 데 에너지가 필요하다`, `겅중 → 긴 다리로 뜀`. Removing punctuation, changing endings, or appending `scene/process/thing` does not make a narrated event eligible. An independent verb lemma such as `떨다` remains an allowed **word**, not an event description.
- **Mandatory independent containment/derivation gate (initial Candidate review only):** From the actual changed Candidate file and matching Canonical lemmas/Senses, extract **all** source-lemma ↔ candidate pairs where either normalized string contains the other (ignoring spaces/hyphens), then verify there are **zero** matches. **Every match is a Stage 1 `-1` blocker without exceptions**; do not override for synonyms, dictionary status, semantic independence or writer-facing imagery. Both `개 → 개집` and `반송 → 반송파` must be excluded. Independently search shared-stem, suffix/ending and near-form derivatives **not caught by containment**, e.g. `발라드 → 발라더`, and assess their actual source Sense for triviality; `마련하다 → 마련`, `박제하다/박제되다 → 박제`, `발버둥질 → 발버둥`, `반자동 → 반자동식`, and `마흔 → 마흔 살` are also forbidden. Producer scans and Candidate v1 success never substitute for this independent check. Report actual checked scope and exact `(record_id, sense_id, candidate)` for confirmed blockers; no per-candidate receipts or second blanket semantic review are required. **Candidate follow-up rounds retain the narrow review boundary below**, rather than restarting the initial full check.
- **Risk-first review protocol:** read the *full changed-path list*, then target **(1) sentence/verb-phrase patterns, (2) lemma-containing words and phrases, (3) multiword gloss-like/collocational expressions, (4) ordinary standalone words as positive controls** against actual Canonical lemma and bound sense. Search/inspect enough changed candidates across the affected batch to establish whether a defect is systemic; do not pretend a small sample or a schema-only CI pass is a census. **Any confirmed forbidden sentence, clearly trivial form/derivation/repetition under this Stage 1 policy, or self-repetition is a `-1`; demonstrable repeated mechanical gloss restatements or disguised clauses are also production-form `-1`, consolidated by defect class, but ordinary scene/image associations are not blockers merely for being conventional**, not one comment per word. If a single questionable expression is genuinely debatable, leave its admission value to Relation Factory Stage 2 instead of imposing a blanket subjective cutoff. Fix the general producer/checking rule for future batches rather than requesting only example-word substitutions.

**Candidate review-round boundary (A/B/C/D):** The consolidated Stage 1 **initial review is the one broad candidate discovery round**: investigate suspicious classes sufficiently and enumerate the **exact `(record_id, sense_id, candidate)` targets** requiring correction in its first `-1`. A defect-class explanation or illustrative examples do **not** create open-ended authority to demand additional unchanged candidates in later rounds, and authors must not be told to re-audit the full batch as a review fix. **Follow-up reviews are resolution rounds**, not another batch hunt: assess only previously reported targets (including still-relevant blockers from the former review policy), the author's corrections or reasoned objections, the old-HEAD → new-HEAD candidate delta and its direct regressions. Verify every removal preserves eligible candidates; inspect newly added/modified strings. **If an unchanged, unreported candidate is noticed late, record the initial-round coverage miss as non-blocking feedback or propose separate future producer/quality work; never append that candidate to a new `-1` on the same data PR merely because it resembles an earlier class.** Neither a new HEAD nor the final Stage 2 gate creates another initial discovery round.

**Candidate preservation and deletion-diff audit on blocker fixes (all A/B/C/D):** Removing a forbidden candidate can resolve a blocker; **removing an eligible independent word as collateral damage is a separate Stage 1 regression**. Evaluate both the corrected output and what disappeared.

- **Track the entire fix, not just the last commit:** on Candidate re-review, compare the last substantively reviewed pre-fix candidate snapshot (and the initial pre-fix snapshot when fixes span multiple commits) with the current HEAD by `(record_id, sense_id, candidate)`. Enumerate and count removed, added and replaced candidates; inspect the **negative diff** as well as surviving strings. A clean Candidate v1 validator or an author's "fully rechecked" claim does not establish that deleted candidates were ineligible.
- **Require source-bound reasons, preserve legitimate discoveries:** the author should report the removal count, actual defect classes and relevant positive controls, grouping explanations rather than writing one comment per word. A removal needs evidence that the candidate violates **Stage 1 output eligibility** (e.g. a disguised clause, routine gloss fragment, exact self-repetition or an unmistakably wrong source sense). **Not appearing as a Canonical headword/search form, being present in a gloss, unfamiliarity, different POS, weak/indirect association or low anticipated Tier is not by itself a reason to delete an independent word or compact meaning-extending scene/image/sensory expression**. Except for the **mandatory normalized source-lemma↔candidate containment exclusion**, do not purge by blanket dictionary membership, gloss-token, unrelated substring, suffix or "metadata word" filters; assess the actual lexical item and bound sense. 
- **Independently verify deletions:** group the removed set by the claimed failure mechanism, inspect the removed candidates against their exact Canonical source senses, and challenge overly broad groups with **valid standalone-word and concise scene/sensory-expression positive controls** as well as truly invalid gloss paraphrases. Expand inspection to affected removals when a broad filter is demonstrated; do not mistake sampling for exhaustive verification. If an eligible word or compact meaning-extending expression was removed without a concrete Stage 1 eligibility failure, require restoration or a substantiated correction and retain `-1` until resolved. Genuine Stage 1-ineligible strings should stay removed. **Relation Factory Stage 2 determines the eventual relation admission/Tier of preserved words; Candidate review does not.**

This focused form gate is **separate from the lenient Stage 1 treatment of weak but intelligible word relations** and from Relation Factory Stage 2's admission/editorial judgment. Do **not** add a brittle universal regex/sub-string/word-count blocker or require all words to appear literally in a gloss.

## 3. Stage 2 — final gate and squash merge only

Stage 2 **exclusively owns CI status verification**: verify the current PR/issue and **unchanged HEAD**, an effective evidence-bearing consolidated technical PASS for that HEAD, a **successful required GitHub Actions PR CI check on that exact HEAD**, and no unresolved `-1` or contradictory evidence. Consume technical PASS with Section 7's tolerance and the transition rule in Section 1; verify that its scope and blocker closure support the gate without repeating the technical audit. **Do not classify changed files, choose CI tiers or reproduce the workflow's run/skip rules**; `.github/workflows/ci.yml` selects and executes CI. An unrelated green check or a check for another HEAD does not suffice.

Pending, failed, missing or stale required CI **blocks merge, not the technical `+1`**. Surface an actionable CI failure or missing gate and recheck its result later; a same-HEAD CI rerun does not require another Stage 1 review or replacement PASS. A correction that creates a new HEAD returns to Stage 1 for focused verification of that change and any unresolved blockers. An uncertain final gate or stale review marker also blocks merge. Route concrete contradictory technical evidence to Stage 1; CI state alone is not a technical `-1`.

If all gates hold, **squash-merge using the expected exact HEAD SHA**. Do not perform another broad technical/semantic audit, commission a new probe, require a second technical PASS or new `+2`, issue GitHub APPROVE/REQUEST_CHANGES, or wait for post-merge master CI.

## 4. Risk routing — load relevant guides, not every guide

- Lexical data, schema, senses, relations, editorial QA, canonical/admission: **read `docs/review-data.md`** and apply **`docs/relation-editorial-policy.md` as the current owner decision**. `direct`/`antonym` require source-bound semantic similarity/opposition, which may be established by a plausible, recurring natural use context; do not require exhaustive gloss equivalence, universal sentence substitutability or logical exclusivity. A reviewer should state the plausible context before deciding a material mismatch remains. Writer-facing `near`/`mood`/`scene`/`sensory`/`action`/`association` are **preserve-first**, judged primarily on same-source/group relevance 1–9, not strict substitutability.
- **Issue #838 말의 결/연상:** `docs/relation-editorial-policy.md` ("Scope of Issue #838") and `docs/review-data.md` define the contract; this file does not require reading any other instruction file. Review the actual relations and Tiers (연상 Tier 1 = informal-synonym-candidate level, relative within the same source/group, no quotas) normally. ID targets must bind the exact headword/homograph/sense; text-only targets must be non-clickable with no reverse and no invented ID; authored ID↔ID relations are explorable both ways. Verify text-only and bidirectional behaviour against the implemented code; do not accept data that relies on unsupported behaviour. `data/headword-candidates/pr-<PR number>.jsonl` is checked only for JSONL/Schema v1 conformance, a real `source_record_id`/`source_lemma`, and obvious junk or a candidate whose same meaning is obviously already an existing headword (same `term` with a different `meaning_hint` is a distinct valid candidate; never reject by spelling alone); promotion merit and deep candidate QA are not `-1` grounds.
- Search, ranking, normalization, candidate eligibility and ordering: **read `docs/review-search.md`**.
- CI, validators, factory/build, SQLite, generated artifacts and test policy: **read `docs/review-toolchain.md`**.
- Extension, UI, Chrome APIs, MV3, storage and WASM: **read `docs/review-extension.md`** when touched.
- External sources, provenance, licensing or distribution: **read `docs/review-licensing.md`** when touched.

For a data pipeline touching multiple boundaries, trace **candidate → source-bound semantic QA → admission → canonical → direct search** and load each relevant guide. Keep current and historical evidence distinct; do not let producer self-check masquerade as independent/human QA. Apply existing owner decisions, but never infer third-party redistribution rights from public R&D visibility.

## 5. Non-negotiable blocker discipline

**Corpus-backed C/D Candidate reviews — execution vs. reporting:** C's owner-approved #1155 procedure (and D's #1156) governs actual production: correct source-sense VERIFIED contexts, required independent exploration, truthful local evidence, and eligible Candidate v1 outputs are substantive requirements. A **demonstrated** omitted exploration pass, false VERIFIED attribution, wrong-sense candidate, fabricated execution evidence, invalid output, or systematic improper candidate deletion is a technical `-1` with a concrete affected case or supported failure mechanism. The producer's PR summary is not itself independent proof of private corpus inspection; do not substitute a perfectly balanced table for source-bound quality review.

**PR-body reporting is non-blocking (all methods and stages):** Method issues may prescribe a minimum execution summary, counts, sources or validation facts for authors to report, but **missing or incomplete PR-body fields, transcription mistakes and inconsistent summary numbers are never a `-1` by themselves**, even if the issue calls the summary mandatory or a public gate. Give a concise, non-blocking correction instruction in an otherwise technically passing `+1`; do not wait for a rewritten description, new commit or new HEAD to issue PASS. Conversely, a polished PR body does not prove the work was performed. If independent technical evidence establishes that a required sweep, source-sense verification, provenance boundary or output invariant was actually violated, issue `-1` for **that concrete production defect**, not for missing narrative evidence. Suspicion based only on absent PR-body details or inability to independently inspect private records is not proof of failure. Do not demand exhaustive private-ledger disclosure or per-lens accounting tables. On re-review, assess author explanations on their merits and close resolved technical objections promptly.

**Test and validator discipline:** Tests exist to protect product stability and established invariants, **not to maximize code coverage**. Review both the sufficiency **and necessity** of added checks. Before demanding a new validator/test or raising `-1` for missing coverage, demonstrate a plausible failure through a supported production path or an explicitly required security, licensing, or trust boundary; its material impact; and why existing checks do not suffice. Do not invent unreachable states solely to expose validator blind spots. Manually corrupting a correctly generated, read-only SQLite artifact is not, by itself, a production defect or grounds for a blocker—even if a generic provenance check could detect more mutations. Prefer the smallest shared protection, and weigh its implementation, recurring CI, maintenance, and review costs against actual regression-prevention value. Challenge redundant or artificial-only tests; do not demand them.

For a **shared defect**, demand a real failing example, correction at the common producer/validator/admission/consumer boundary, an **old-fails/new-passes shared regression** and enforcement for **all applicable existing records and future additions**. Reject example-only data patches and batch/word-specific regression memorization. Apply the review-round boundaries in Section 2: a shared-cause finding does not reopen unchanged, unreported Candidate targets on follow-up. Neither missing required validation nor false provenance/approval evidence can pass.

**Subjective lexical correctness is source-bound editorial judgment**, not an excuse to introduce blanket mechanical synonym validators; a valid entry with zero relations must remain eligible. For `direct`/`antonym`, assess the bound meanings and a plausible recurring usage context: meaningful similarity/opposition can survive different gloss emphasis, non-universal substitutability, or coexisting qualities. Before `-1`, explain why no plausible natural context supports the actual relation; topic-only, co-occurrence, causation and a contrastive scene alone are insufficient. The owner-approved comfort/discomfort, culinary sour/sweet, literary realism/hallucination, 차분하다/침착하다 and 늪/습지 calibrations are documented in `docs/relation-editorial-policy.md`. For exploratory relations, prioritize an intelligible creative path and compare **relevance against existing and proposed peers of the same source sense/UI group**; downrank marginal ideas instead of vetoing them. A subjective category preference or 4-vs-5 band difference is not a `-1`; demand a demonstrated material error or significant, evidenced rank inversion. Respect fail-closed holds/admission and source rights. For CI/canonical architecture changes, preserve one complete-revision context, the global semantic audit, shared in-memory projection reuse and the **zero-current-Canonical SQLite-build invariant** in all automatic CI paths. The separate SQL schema gate owns actual Full/Lite builds; see `docs/review-toolchain.md`.

## 6. Required exact-HEAD CI status

Stage 2 confirms that the **required GitHub Actions PR CI check completed successfully for the exact reviewed HEAD** before merging. The workflow alone decides which validations run or skip; reviewers do not maintain a second set of path, tier, schema or skip rules. A pending, failed, missing or stale check is not a merge pass. Stage 1 does not retrieve or use CI results in its technical judgment.

## 7. Technical GitHub PR review record (Stage 1)

Write **exactly one final GitHub PR Review COMMENT** per Stage 1 run (`gh pr review --comment`, **not** `gh pr comment`); never APPROVE/REQUEST_CHANGES. Verify HEAD again before submitting; never PASS an unreviewed new commit.

**Mandatory submission prefix:** line 1 is **exactly** `+1` or `-1`; line 2 is **exactly** `HEAD: <40-character lowercase hex SHA>`. No heading, bullet, code fence, whitespace or empty line before/between these lines. All prose/evidence follows line 2 (a blank line afterward is allowed). A review without substantive evidence is never sufficient. New technical reviews use `+1`; historical `+2` remains readable under Section 1's transition rule.

**Technical PASS consumption:** Stage 2 must accept a malformed prefix **only if the same review unambiguously records technical PASS/`+1` (or a qualifying historical `+2`), identifies the exact current 40-character HEAD somewhere, and contains substantive evidence for the applicable technical scope**. Do not block or demand resubmission solely for formatting or the technical reviewer having seen/mentioned CI; disregard those CI claims. Missing/contradictory evidence, ambiguous PASS or stale/wrong HEAD still fails. Producing reviewers must themselves use the **strict** prefix.

Record stage, issue/scope, approach/boundaries, actual reviewed evidence, confirmed blockers (or none), uncertainties/unrun checks and the SHA-bound conclusion, **without CI claims**. On initial `-1`, consolidate confirmed targets, root cause/impact, safer correction and required verification. On re-review, briefly account for **all** prior unresolved technical blockers, relevant author replies, accepted/withdrawn/maintained findings and why, the actual fix delta and direct regressions, including when HEAD is unchanged. Do not add a second-reviewer critique or mandatory probe report.
