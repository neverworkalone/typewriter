# D 생산·검증 절차 V2 (배치 공통, 단어별 예외 없음)

이 문서는 `docs/relation-factory.md`의 **D(말뭉치 실제 쓰임)** 목적을 그대로 유지하면서, V1에서 확인된 세 가지 결함을 일반 규칙으로 막는 절차를 정의한다. 특정 표제어·sense를 위한 분기나 예외 목록은 두지 않는다. 출력 계약은 Candidate JSONL v1 그대로이며, 근거(원문·문단 ID·검색 로그)는 로컬에만 두고 Git에 올리지 않는다.

## 1. V1에서 확인된 결함 (감사 근거)

| 결함 | V1 실측 |
| --- | --- |
| 뜻풀이 재작성/무근거 후보 | 247개 중 33개(13.4%)가 뜻풀이 어휘만으로 구성, 137개(55.5%)가 검색 창에서 확인되지 않음 |
| 표제어 재제시·인접 sense 혼입 | 14개가 source lemma를 부분 문자열로 포함, 같은 record의 다른 sense와 후보 중복 1건 |
| 검색 실패의 침묵 | 2글자 질의는 trigram FTS가 오류 없이 0건을 반환하고, bigram sidecar는 고빈도 항목의 postings가 비어 있음(해당 23개 sense) |

V1은 검색 결과 0건과 "검색 자체가 불가능했음"을 구분하지 않았고, 후보가 검색 창에 있었는지 확인하는 단계가 없었다.

## 2. 검색 계약 (일반 규칙)

1. **sense 결속:** `sense_id`, 품사, 뜻풀이를 먼저 고정한다. 표제어만으로 검색하지 않는다.
2. **질의 표면:** 용언은 어간(`다` 제거)을 쓴다. `하다` 용언은 어간과 `했/한/할/함/해/하` 결합형을 함께 조회해 명사 용례가 동사 sense를 대신하지 못하게 한다.
3. **경로:** 3자 이상은 trigram FTS, 2자는 bigram postings, postings가 없거나 NULL이면 `LIKE` 전량 조회로 대체한다. 공백이 있는 표현은 FTS 결과와 무관하게 `LIKE`로 정확 일치를 확인한다.
4. **상태 구분:** sense마다 `ok` / `zero_hits` / `zero_after_filter` / `search_failed`를 기록한다. `search_failed`는 빈 후보로 쓰지 않고 재시도한다. `zero_hits`만 빈 배열의 근거가 된다.
5. **근거 보관:** sense별로 창(문단 텍스트 + 문단 ID)을 N개 저장한다. 창 선택은 균등 분산 + 뜻풀이 인접을 섞어 확증 편향을 줄인다. 원문·ID·로그는 저장소 밖에 둔다.

## 3. 후보 추출 규칙 (일반 규칙)

1. 후보는 **인용한 창 하나에서 어휘 근거가 확인되어야** 한다. 정확 일치 또는 어간·어미 변화(어간 2자 이상, 마지막 모음 탈락 포함)까지 허용한다.
2. 후보는 source lemma를 부분 문자열로 포함할 수 없다(합성어 재제시 금지).
3. 후보는 같은 record 다른 sense의 표제어와 같을 수 없다.
4. 같은 record의 두 sense에 같은 후보를 쓰려면 서로 다른, 각각 검증된 창이 있어야 한다. 그렇지 않으면 한쪽만 남긴다.
5. 창의 용법이 다른 sense에 속하면 그 창에서 후보를 만들지 않는다.
6. 후보 개수 목표는 없다. `zero_hits`이거나 방어 가능한 연결이 없으면 빈 배열을 쓴다.

## 4. 검증 게이트 (자동, 일반 규칙)

입력: 후보 + sense별 창 + Canonical.

- **G1 근거:** 후보의 모든 내용 토큰이 인용 창에서 확인되고(정확/어간/어미 변화), 그중 최소 하나는 강한 일치여야 한다. 실패 → 제거.
- **G2 자기 표제어:** 후보가 source lemma를 부분 문자열로 포함 → 제거.
- **G3 인접 sense:** 후보가 같은 record 다른 sense의 표제어와 동일 → 제거.
- **G4 뜻풀이 재작성:** 내용 토큰이 2개 이상인 후보가 모든 토큰에서 뜻풀이와 겹치면 제거(단일어는 문맥에 실재하면 근사어로 허용).
- **G5 상태:** `search_failed` sense가 하나라도 있으면 산출을 중단하고 재수집한다.

게이트 임계·규칙은 배치 전체에 동일하게 적용하며, 단어별 예외를 두지 않는다. 규칙을 바꾸면 버전을 올려 모든 배치에 다시 적용한다.

## 5. 독립 재검증 (수동)

최종 출력 직전에 후보마다 **별도 패스**로 다음을 다시 본다: (a) 인용 창이 정확한 sense의 용법인가, (b) 후보의 연결이 창에서 설명되는가, (c) G1~G4를 통과했는가. 약한 근거(어미 탈락으로만 일치) 후보는 창 원문을 다시 읽고 남기거나 버린다. 버린 항목과 사유는 로컬에 기록한다.

## 6. 출력·검증

`{"record_id":..., "senses":[{"sense_id":..., "candidates":[...]}]}` 한 줄 = 한 record. Canonical 배치의 모든 record·sense를 순서대로 포함한다. 제출 전 `scripts/relation/candidate-contract.mjs`의 `validateCandidateBatch`를 해당 샤드·배치로 실행한다.

## 7. 보고 의무

- 상태 분포(`ok` / `zero_hits` / `search_failed`)와 빈 후보의 성격을 함께 보고한다. 빈 후보는 미실행이 아니다.
- 검색 경로별 사용 횟수( FTS, postings, LIKE 대체 )를 보고한다.
- 게이트 제거 내역과 독립 재검증 내역을 보고한다.
- 후보 수는 품질 지표가 아니며, 최종 채택·등급 판정은 Stage 2와 독립 평가자의 몫임을 명시한다.
