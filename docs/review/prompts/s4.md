# S4 Selective Polish — focused PR technical review

Read this PR HEAD's root `REVIEW.md` first. This card is for `[S4/<model>] <SSS>` data PRs under standing production issue #9929 (implemented by #9928). It is PR review Stage 1 (technical `+1`/`-1`), not the final Stage 2 exact-HEAD CI/merge gate. **S4 review is a format and technical review only; it does not re-review meaning or editorial content (#10268).** Route a PR that also changes implementation through `code.md`.

Stage 4 Polishes only the confirmed `d:"p"` Senses from `data/relation-selection/selection-SSS.jsonl` (#10174). It edits approved Relations in both directions, including `s` counterparts, so Relation files of **other shards** may change too. Stage 4 is Relation-only (#9929). Stored-data and CLI contracts are in `docs/relation-factory.md` §4-E and §5.

## Responsibility boundary

The S4 committer is the vocabulary editor. The committer alone is responsible for expression value, Add/Drop, redundancy and the representative form, the semantic choice of Sense, and the editorial fit of Type/Tier (`docs/relation-editorial-policy.md`, *Polish and Stage 4*). The reviewer does not re-judge them.

| Committer's judgment — not S4 review | Technical contract checked by S4 review |
| --- | --- |
| Is it a useful expression or literary/indirect association for a writer? | Is the change on the allowed data path and within the editing scope? |
| Is an Add or Drop worth it; is a useful expression lost? | Is the actual change applied through the official edit path and the relation-key contract? |
| Is it a repeat of the same choice; which form stays as representative? | Do the stored keys keep structural integrity (no duplicate or reverse duplicate)? |
| Which Sense fits best in meaning? | Does the ID exist and bind exactly to the current input, owning shard and allowed scope? |
| Which Type/Tier shows the expression better? | Are Type and relevance allowed values, and are existing type-specific structure/POS constraints met? |

- **Reading glosses to argue that another Sense fits better is content review.** It is not reintroduced as an "obvious Sense error" exception. A technical binding error is different: an ID that does not exist, or an input number mapped to the wrong actual ID.
- Do not request a change, restoration, Add, explanation or re-judgment because an expression is unfamiliar, an association is weak, a better expression exists, or many items were dropped.
- Do not reselect the confirmed P/S/E. Constraints that the existing inputs and code enforce still hold, but do not expand them into re-classifying glosses.
- A technical `+1` means this technical scope passed. Never record that meaning quality was independently re-reviewed.

## Initial review — technical contract

Use the existing official checks and execution evidence. Do not build a new verification layer or duplicate automated validation as row-by-row AI checks.

1. **Changed paths:** the actual merge-base → PR HEAD change is limited to `data/relations/relation-*.jsonl`. Relation changes in other shards that own the Relation are allowed. A change to Canonical, Candidate, Drop (`data/relation-drops/drop-*.jsonl`), selection files or generated outputs is outside an S4 production PR.
2. **Editing scope:** Relations that touch a confirmed `p` Sense of the shard, plus the rebinds the current contract allows. `s` counterparts are not forbidden; confirmed `e` and other authoring constraints enforced by existing code remain.
3. **Stored integrity:** ID existence and binding, allowed fields and values, relation keys, duplicates and reverse duplicates, owning shard of storage, provenance, two-way projection of ID Relations and the text-only contract. Official `direct/antonym` and Canonical stay protected.
4. **Apply integrity:** apply/amend/replay follow the official relation-key path, resolve real key conflicts and keep unrelated valid changes. Do not demand restoring an old whole file or reopening a completed batch.
5. **Execution completeness:** the existing distinction of completed, Policy Skip and failure holds. An actual defect that turned a technical non-processing into a normal edit or no-change is a technical finding. Do not infer an execution failure from missing PR-body counts or explanations alone.

Stage 4 never writes `p`/`z`, removes no Drop and runs no Candidate accounting, so do not demand Candidate/Drop reads, accounting comparison, orphan calculation, `p/z` rows or extra receipts.

**Cost:** check the complete changed-path list and the technical evidence needed. Do not read every changed Relation's gloss or surrounding Relation list for meaning review. Use existing read-only queries such as `node scripts/relation/s4-cli.mjs decisions --shard SSS --base <merge-base>` (`--senses <id,...>` for named Senses) only as far as needed to settle a concrete technical doubt. Reuse existing verify results; do not expand into repeated full re-verification, builds, per-row CLI calls or a separate shard audit.

## Blockers, committer replies and re-review

- Judge `+1/-1` on **technical defects only**. Do not query or wait for CI, and never merge.
- **`-1`:** give every technical problem you found at once. For each, name the exact file/relation key or input range, the technical contract violated, the actual impact and the evidence. Do not restate a semantic or editorial preference as a technical defect.
- **Re-review** covers only the earlier findings, the committer's actual replies, changes made since, and their direct regressions. Do not raise new findings against unchanged, unreported relations.
- A valid rebuttal, or withdrawal of a finding outside this scope, is resolved without data changes. Do not demand a dummy commit. Once every finding is resolved and no direct regression remains, record a substantiated `+1`, also on the same HEAD.
- Missing or incomplete PR-body explanation or counts alone is never a `-1` (`REVIEW.md` §5).

## Roles

Only review Stage 1 does this technical review. Final review Stage 2 checks a valid same-HEAD technical `+1`, no unresolved technical blocker and the required exact-HEAD CI, then merges at the expected HEAD. It does no semantic re-review and adds no extra PASS. A Stage 1 technical PASS is not a CI or merge claim.
