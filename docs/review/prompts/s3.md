### Relation Factory Stage 3 editorial data PRs (#2455) — separate from PR review stages

Apply this specialization to a verified Stage 3 editorial data PR such as current `[S3/<model>] SSS` (or historical `[Relation Stage 3] SSS`), only when actual changed files match its allowed Relation/Drop scope. The Stage 1 `+1` and final Stage 2 exact-HEAD CI/merge gate apply. Factory Stage 3 independently **audits the same writer-facing editorial standard now owned by Factory Stage 2** (#2544), correcting the admitted Relation set when needed; its existing Drop and Link Repair capabilities are unchanged. Earlier preserve-first Stage 2 data were produced under their then-current rules. The **repeated production/task instructions** belong to [#2455](https://github.com/neverworkalone/typewriter/issues/2455); the data contract belongs to [Relation Factory](../../relation-factory.md).

- **Scope and diff:** The data PR may change only its shard's `relation-SSS.jsonl` and `drop-SSS.jsonl`, by deleting existing Relation rows or repairing existing text-only rows to an exact ID while preserving Type/Tier. Use the **actual merge-base → PR HEAD diff** and the compact `edit-cli report` when available; the final Drop file alone cannot identify deleted Relation meanings.
- **Link Repair — review every change:** Check the source Sense and **all same-spelling competing target Senses with full glosses**, exact ID/spelling, preserved Type/Tier, duplicate/reverse conflicts and correct bidirectional projection. A wrong-Sense ID is a blocker; a first-spelling match is not evidence.
- **Drop — risk-based editorial sampling:** Inspect actual deleted rows, high-deletion Senses, redundant inflections/repetitions, suspicious Sense mismatches and positive controls for **valuable imagery/associations**. Consider the reverse-direction value of deleted ID rows. Do **not** repeat the full-shard AI edit, demand per-row essays or enforce a deletion quota.
- **Objective integrity:** Verify the existing Relation/Drop and build gates, shard-owned `by:"z"` orphan candidate accounting, surviving alternate Sense links and intended forward/reverse effects. `z` records an orphaned Candidate after Relation deletion; it does not claim that the Candidate is semantically unrelated. Confirm no surviving Relation or reverse coverage still answers it. Cross-shard reconcile may only treat **proven coverage loss from an actually merged Stage 3 ID deletion**; unrelated `missing` is not automatically a Drop. Apply the detailed invariants of the linked task/data contracts rather than duplicating their algorithms here.
- **Blockers and follow-ups:** Block demonstrated corruption, wrong Sense binding, broken candidate accounting, unintended Relation removal or **systematic** loss of useful language. Ordinary editorial taste differences and borderline examples are non-blocking. Subsequent rounds focus on reported defects, author responses, fixes and direct regressions—not a fresh shard sweep.
- **Review cost:** Reuse existing validation and Full/Lite SQLite checks. Do not demand new audit receipts, document/policy SHA proofs, sense-list hashes, another complete semantic pass or new UI automation. **Documentation/instruction-only PRs use `no-review`; implementation and Stage 3 data PRs require normal review.**

## Operational boundaries for reviewers

- Source authority: `docs/relation-editorial-policy.md` for writer-value decisions and `docs/relation-factory.md` for the Stage 3 stored data contract. #2455 defines how the producer runs; its private chunk work is not an additional independent reviewer execution obligation.
- **Link Repair:** examine every actual text-only → ID correction, all same-spelling competing target Senses with glosses, exact target ID, retained Type/Tier, bidirectional result and collisions. A first spelling match never proves correct Sense binding.
- **Drop:** sample changed/deleted Relations by risk, including high-deletion Senses and valuable word/image positive controls. Judge writer-facing independent expression value and impact on reverse coverage. Stage 3 may create `by:"z"` orphan accounting only when no valid Relation/reverse covers the Candidate, not a new S2 editorial `x/e` or Supervisor `f`. Preserve prior valid S2 decisions unless a concrete reason for change exists.
- Require actual scope, verification evidence and correct saved accounting; reuse existing CLI validation (e.g., shard verify) and avoid re-editing the shard or demanding a new corpus audit. After a blocker, examine earlier targets, changed rows and direct regressions, not the entire shard again. Final PR Stage 2 alone checks exact-HEAD CI and merges.
