# Meaning 편집 계약 — 동음이의어 중심 (#764)

`data/canonical/`의 STDICT record/sense를 Typewriter 작가가 사용할 Meaning으로 편집하는 계약이다. 데이터 구조·검증 경계는 [meaning-layer.md](meaning-layer.md), 재편집 실행 범위는 [Issue #764](https://github.com/neverworkalone/typewriter/issues/764)를 따른다.

## 현행 기준과 적용 우선순위

- **#764의 현행 Meaning 정의는 '독립된 어휘적 정체성'이다.** 하나의 어휘가 여러 뜻·비유·용법으로 확장되면 **1 Meaning**으로 묶고, 우연히 같은 표기를 공유하는 **독립된 동음이의어**만 분리한다. 원본 STDICT sense 하나당 Meaning 하나도, 가까운 뜻풀이끼리만 합친 묶음도 목표가 아니다.
- **#764 Meaning 재편집과 이후 해당 기준을 명시적으로 채택한 작업**에서는 본 문서의 현행 기준 및 #764의 판정 예시를 적용한다. #715 Pilot 및 #716 전량 편집의 이전 분리 기준·승인된 판정·리뷰 의견이 충돌하면 **#764의 새 의미 판정이 우선**한다. 특히 '문자적 의미와 비유적 의미의 지시 대상이 다르다'는 이유만으로 분리하지 않는다.
- **#716에서 수행된 판단 및 리뷰의 당시 유효성을 소급 부정하지 않는다.** 본 문서 뒤쪽의 #715·#716 표·판정·감사 기록은 변경하지 않는 **역사적 이력**이며, #764 작업을 차단하는 규범이 아니다. #716의 진행 중인 PR에 새 편집 작업을 묵시적으로 추가하지 않는다.
- 최신 PR HEAD의 루트 `REVIEW.md`는 PR 리뷰 **절차**를 규율하고, 본 계약과 해당 Issue는 #764의 Meaning **편집 내용**을 규율한다. 검증·리뷰에서 양쪽을 혼동하지 않는다.

## 판정

| 판정 | 현행 의미 | 결과 |
| --- | --- | --- |
| KEEP | 다른 Meaning과 통합할 자연스러운 어휘적 연결이 없는 **독립 동음이의어**, 또는 처음부터 하나뿐인 Meaning | 독립 Meaning으로 보존 |
| MERGE | 동일 어휘의 여러 sense/용법/의미 확장 | 하나의 Meaning으로 합치고, 전체 용법을 대표하는 Typewriter gloss 작성 |
| GLOSS EDIT | Meaning의 sense 결합은 맞지만 원본 gloss가 참조형이거나 통합 의미를 명확히 설명하지 못함 | sense membership을 바꾸지 않고 Meaning-layer gloss만 수정 |
| DROP `duplicate` | 같은 lemma에서 원본 sense가 **명백하게 중복**되어 별도 보존의 의미가 없는 경우 | `data/adjudication/`에 생존 sense인 `duplicate_of` 기록 |
| DROP `out_of_scope` | 현재 제품 수록 범위 밖이라는 명시적 개별 판단 | `data/adjudication/`에 기록하고 `duplicate_of`를 두지 않음 |

**다의어 통합(MERGE)은 중복 삭제(DROP)가 아니다.** 서로 다른 용법의 source sense를 모두 보존하고 하나의 Meaning에 연결한다. canonical의 원본 sense/gloss는 변경하지 않는다.

## 현행 편집 원칙 (#764)

1. **표제어의 '뜻 개수'가 아니라 '독립된 단어 개수'를 판정한다.** 동일 lemma의 모든 canonical record/sense를 먼저 펼쳐 전체를 비교한다. STDICT의 record/동음이의어 번호·sense 번호·품사 경계는 참고 정보이지 자동 분리 기준이 아니다.
2. **하나의 어휘에서 자연스럽게 이어지는 의미 확장이라면 MERGE한다.** 물리적/심리적, 문자적/비유적, 구체적/추상적 의미, 대상·상황·논항·문법·품사·표현 방향의 차이, 용법별 유의어 목록의 차이는 그것만으로 분리 사유가 아니다. 실제 자연스러운 의미 관계를 개별 판단하며, 문법적으로 역할이 달라졌다는 이유만으로 독립 어휘라고 단정하지 않는다.
3. **명백한 독립 동음이의어는 분리한다.** 단지 추상적인 단어 하나로 억지 연결하거나 표기·발음의 동일성만으로 병합하지 않는다. 실제 한국어 사용에서 서로 독립된 어휘로 이해되는지를 원본 뜻풀이와 용법을 근거로 판단한다. 독립성의 입증 없이 '지시 대상/전문 분야/문법 기능이 다르다'는 사유만으로 KEEP하지 않는다.
4. **필수 기준 사례 — `쌀쌀하다`: 1 Meaning.** 날씨·바람이 차갑다는 문자적 용법(`w455618-s1`)과 사람의 성질·태도가 차갑다는 비유적 용법(`w455618-s2`)은 '차가움'이라는 하나의 어휘적 개념이다. `서늘하다/춥다`와 `냉담하다/매정하다`처럼 용법별 유의어가 달라도 분리하지 않는다.
5. **필수 기준 사례 — `꽃밭`: 1 Meaning.** 꽃이 실제로 핀 장소와 아름다운 사람들이 모인 곳이라는 비유는 같은 어휘의 확장이다. #716 당시 '현실 장소와 비유적 독립 지시 대상을 나눠야 한다'는 판단을 #764에 적용하지 않는다.
6. **필수 반대 사례 — `배`, `눈`: 동음이의어 분리.** `배`의 과일·선박·신체 부위, `눈`의 신체기관·하늘에서 내리는 눈은 서로 독립된 Meaning이다. 다른 원본 sense가 있으면 같은 기준으로 추가 판정한다.
7. **재판정 대상 — `끼다`.** #716 결과의 Meaning 수를 답으로 전제하지 않는다. 전체 record/sense를 한꺼번에 보아 독립 어휘 정체성이 실제로 몇 개인지 결정한다. 특정 개수를 선험적으로 강제하지 않는다.
8. **대표 gloss는 '하나의 개념'을 먼저 설명한다.** 포함한 원본 sense의 주요 용법은 빠뜨리지 않되, 서로 관계없는 뜻들을 쉼표나 '또는'으로 나열한 것만으로 병합의 근거가 되지는 않는다. canonical에 없는 새로운 의미를 지어내지 않는다.
9. **과도한 분리와 과도한 병합을 모두 검토한다.** 리뷰에서 과도한 병합을 지적하려면 실제로 **독립된 동음이의어가 하나로 묶였다는 source-bound 근거**를 설명한다. 문자/비유, 온도/태도, 용법별 유의어·지시 대상의 차이만으로는 #764의 병합 블로커가 아니다. 반대로 과거 KEEP 관성이나 gloss 문자열 유사도 필터로 검토 대상 자체를 생략해서도 안 된다.
10. **기술적 불변조건은 유지한다.** 서로 다른 lemma의 sense는 합칠 수 없다. 동일 lemma 내 여러 record의 sense는 하나의 Meaning에 포함될 수 있다. DROP `duplicate`는 진짜 중복에만 적용하며, 그 대상 sense와 `duplicate_of`의 유효성을 확인한다. MERGE 대표 id는 기존 canonical 순서상 첫 구성원의 meaning id(`mNNN_K`)를 따른다. 교차 record MERGE의 대표 record 번호는 가장 낮은 구성 record 번호이며, sense 배열은 canonical 순서를 따른다.
11. **교차 record 병합은 전체 구성과 원천 관계를 대조한다.** 일부 음절·공통 끝 글자·넓은 주제만 겹치는지 보지 말고, 표제어 전체의 명명 원리와 포함 sense의 구체적 뜻을 비교한다. 구성 차이가 독립 어휘 정체성인지 자연스러운 확장인지는 canonical 근거로 개별 판정한다. 병합 구성원의 `direct`가 서로 반의인 target sense로 이어지면 반드시 재검토 신호로 삼되, 관계 하나만으로 자동 분리하지 않는다. 명사·능동형·피동형을 함께 다룰 때에는 품사보다 행위자·상대역·거래 방향을 원문에서 확인하고, 결과가 relation projection에서 올바른 Meaning endpoint와 source provenance를 유지하는지 검증한다. 같은 전체 구성 안의 일반/구체 용법과 자연스러운 확장은 양성 대조로 함께 확인한다. 이 항목은 source-bound 편집 QA 절차이며 기계적 validator 규칙이 아니다.

## 도구와 절차

- 편집 지시는 JSON 스펙(`{ glosses: [{ sense_id, gloss }], merges: [{ senses: [sense id, ...], gloss }], repartitions: [{ lemma, before: [{ id, gloss, sense_ids }], groups: [{ senses, gloss }] }], drops: [{ sense_id, reason?, duplicate_of? }] }`)이다. DROP 사유 생략은 `duplicate`로 취급한다. `duplicate`는 유효한 `duplicate_of`가 필요하고, `out_of_scope`는 `duplicate_of`를 금지한다. `glosses`는 아직 MERGE되지 않은 한 sense meaning의 gloss를 고치며 ID와 sense binding은 보존한다. `repartitions`는 기준 변경에 따라 이미 편집된 한 lemma의 현재 Meaning을 다시 묶거나 나눌 때 사용한다. 각 항목은 현재 행의 ID·gloss·sense 전체를 `before`에 정확히 기록하고, `groups`가 그 sense를 빠짐없이 중복 없이 나눠야 한다. 새 ID는 canonical 초기 투영의 첫 구성 sense에서 결정하며, `data/canonical/`은 읽기만 한다. `node scripts/meaning/apply-edits.mjs <spec.json>`가 적용한다.
- 적용은 제자리 편집이며, 한 lemma 편집이 무관한 shard를 재배치하지 않는다.
- 잘못된 스펙(1개 sense 병합, 이미 병합/DROP된 sense, 중복 편집, 존재하지 않는 sense, 빈 gloss, 다른 lemma 병합, stale `before` snapshot, repartition의 누락·중복·외부 sense, 같은 record든 다른 record든 존재하지 않거나 이미 DROP된 `duplicate_of`, `out_of_scope`에 포함한 `duplicate_of`, 잘못된 reason)은 **전체를 거부**하고 일부만 적용하지 않는다. Repartition으로 다시 만들어진 meaning ID도 기존 lemma shard에 canonical ID 순서로 쓴다. 마지막 Meaning shard의 모든 행을 DROP하면 빈 파일 대신 shard 파일을 제거한다.
- 적용 후 `node scripts/meaning/validate.mjs`(complete)로 모든 canonical sense가 정확히 하나의 meaning에 있거나 DROP 기록이 있음을 확인한다.
- 스펙 파일은 편집 이력으로 보존한다 (`scripts/meaning/pilot-715.json`).

## #764 전량 재편집용 지침(프롬프트)

> 동일 lemma의 **모든 canonical record와 sense**, 이미 편집된 Meaning을 한 번에 확인한다. gloss 단어 유사도나 기존 #716의 KEEP 목록으로 먼저 후보를 제한하지 않는다.
>
> 먼저 **'이 표제어에는 서로 독립된 단어가 몇 개 있는가?'**를 판정한다. 같은 어휘의 문자적·비유적·추상적·구체적·문법적 용법이면 **MERGE**, 서로 관계없는 독립 동음이의어이면 **KEEP**한다. 표제어·원본 record/품사/지시 대상이 같거나 다르다는 형식만으로 결론을 내리지 않는다.
>
> 기준 사례: `쌀쌀하다`(날씨/태도)와 `꽃밭`(실제 장소/사람들 비유)은 **각 1 Meaning**이다. `배`(과일/선박/신체) 및 `눈`(신체기관/강설)은 독립 Meaning으로 **분리**한다. `끼다`의 최종 Meaning 수는 원본 전체에서 새로 결정한다.
>
> 병합 gloss는 핵심 개념을 우선하여 작성하되 포함한 모든 canonical sense의 필수 용법을 보존한다. 사실상 동일한 원본 중복만 `DROP duplicate`로 처리한다. 원본 canonical, provenance, 기존 이력은 보존하고 편집 결과를 기존 `apply-edits` 계약에 맞게 기록한다. 이미 병합된 Meaning을 다시 다룰 때는 저장 결과와 edit spec의 재현 가능성을 확인한다.
>
> 독립 1차·2차 리뷰는 **과도한 분리와 과도한 병합 양쪽**을 평가한다. 이전 #715·#716의 의미 분리 판정을 새 기준보다 우선시하지 않는다. 불명확한 경우 근거를 조사하고 판단 이유를 기록한다; '헷갈리면 기존 Meaning을 모두 KEEP'을 전수 작업 완료의 근거로 삼지 않는다.

### #715 Pilot 당시 경계 사례와 판정 (이력)

- **record 경계**: 같은 lemma의 의미가 같은 sense는 record가 달라도 MERGE한다(`강피밥`, `강피죽`). 의미가 완전히 같은 중복(`전락하다`)은 MERGE가 아니라 DROP duplicate다.
- **접속 기능(`하다`)**: 문법 범주가 같다는 이유로 합치지 않는다. 덧붙임(`s22`)과 나열(`s27`)은 글의 논리 방향이 같아 MERGE, 대립(`s34`)과 역접·결과·조건을 섞은 접속어(`s33`)는 방향이 달라 각각 KEEP. 문법 분류가 같다는 이유만으로 의미를 일괄 합치는 지침을 전량 작업에 확장하지 않는다.
- **조건 vs 이유(`하다`)**: 문법 기능이 비슷해 보이나 의미축이 다르다. 조건(`s30`)은 KEEP, 이유(`s40`,`s45`)만 MERGE.
- **경유 vs 시기 도달(`하다`)**: 단어 의미가 달라 KEEP.
- **작동 ↔ 꺼짐(`가다`)**: 방향이 반대이므로 합치지 않는다.
- **보조 용법의 처리(`보다`, `하다`, `가다`)**: 같은 의미축이면 본동사와 합치지 않고 보조 용법끼리 묶거나 가까운 본동사 축에 포함한다. 새 meaning 유형을 만들지 않는다.
- **사전 `‘사천04’의 원말`**: 참조형 gloss이지만 독립 지시 대상이므로 KEEP. (참조형 gloss 처리는 전량 작업에서 별도 사례가 나오면 판단한다.)

### #716 당시 전량 편집 경계 사례와 판정 (이력)
