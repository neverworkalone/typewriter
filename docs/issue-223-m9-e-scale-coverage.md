## Batch runner contract

`scripts/batch/build-issue-223-corpus-batch.mjs` takes a batch ID of the form `issue-223-m9-e-corpus-batch-NN-YYYYMMDD`; the date is validated and source/pass IDs derive from it. Inventory and canonical IDs continue only from lower-numbered batches, so rebuilding an earlier batch is unaffected by later artifacts. The builder never mints semantic judgments: admitted records require a separately authored `--semantic-reviews` input (one review per admitted lemma, bound to the reviewed gloss digest, with explicit gloss/sense-boundary judgments and diagnostic frames). The input is a bound envelope (`kind: authored-semantic-review-input`, matching `batch_id`, named `reviewer`, `review_status: complete`); each review states its own single-sense boundary outcome and, where the gloss has an ambiguous particle span, its topic outcome (status, state, rationale), and supplies exactly one frame per derived gloss span. The input's SHA-256 is recorded in the output `source_basis.semantic_review_input_sha256`. Missing, unbound, or mismatched reviews fail closed. The builder persists the exact input bytes as `data/batches/<batch>-semantic-review-input.json`; the Issue #223 validator re-reads that artifact, requires its digest, batch, envelope, and admitted-lemma coverage to match, and requires the semantic output reviewer to equal the input's reviewer (the shared validator takes the expected reviewer from config, defaulting to `codex-agent`). The validator also re-derives every semantic decision row from the stored input (same lemma and gloss digest) and requires an exact match, so changing any outcome, rationale, or frame in the output fails even if the artifact digest is recomputed. Only B01–B04 are exempt from carrying an input; any later batch without one fails. Review-only batches need no semantic input.

## Reviewer independence (operating policy)

Typewriter separates producing a batch from reviewing it to manage quality. It is not a security system against a malicious producer, and nothing here is cryptographic proof of identity.

**Owner decision (2026-10-02):** the repository owner accepts the current trust boundary. The reviewer registry `config/semantic-reviewers.json` is an operating policy, not an authenticated identity: the reviewer and candidate-author names are labels written by the batch change itself, and the registry is part of that change. No separate GitHub account, model API key, GitHub App, protected external workflow, or attestation is used. A batch is not blocked merely because it lacks them; a defect in the actual semantic review or a failing existing validation is a normal blocker.

What the contract does enforce:

- the semantic reviewer must be listed in the registry and must differ from the batch's candidate-review author (case-insensitive), in the builder and in the Issue #223 validator, with known-invalid regressions for self-review and unregistered reviewers;
- the review input is bound by digest to the semantic source, and every decision row is re-derived from it;
- from B06 on, the input preserves the reviewers' outcome for **every** candidate (holds included) and binds each cited context index to the candidate's bounded contexts;
- from B06 on, the reviewers' **original outputs stay in local staging**, because repository policy keeps raw model responses and draft text out of `data/batches/` (`docs/repository-structure.md`, `docs/data-policy.md`). The staged file is `reviewer-raw-outputs.json` next to the candidate inventory under ignored `data/reference/`. What is tracked is a metadata-only run record (`*-reviewer-run-record.json`): per run, the context, the candidate range, the digest of the reviewed packet (the packet holds corpus text and is not tracked), and the digest of the staged raw output, plus, for every candidate, the reviewed proposal's disposition and its **gloss digest** (never gloss text). The review input is bound to the run record by digest;
- normal CI (`npm run batch:issue-223:check`, which validates the tracked artifacts and shared lexical admission without a second dictionary build (the shared SQLite artifact is already built and validated once by the toolchain), and the committed-artifact cross-file regressions) checks the tracked artifacts against each other (the independent two-build comparison is a manual validation path, `npm run batch:issue-223:check:deep`, as `REVIEW.md` reserves it for deep/manual validation; it is not registered in `ci:all` because the scheduled Deep CI is already failing on `master` in `tests/m5-12a.test.mjs` for an unrelated historical-replay drift that began with #206). It checks: the run record's coverage and digests, the reviewed proposal digests, and that a reviewer's `fit` is bound to the gloss digest it assessed, so the gloss admitted into canonical data must be the reviewed one and changing a gloss after review is rejected even if the review row is regenerated; that the reviewer outcome and the review row cite the same four verdicts and the same checked contexts; and that review notes are specific to each candidate (a review that reuses one sentence for many candidates is rejected); that each reviewed proposal's disposition (and, for a proposed hold, its basis) is preserved in the run record and must agree with the final candidate review, so a same-lemma disposition or basis change fails even when the hashes are recomputed; that a candidate the author held without proposing a gloss, and in which the reviewer found no lexical blocker, is recorded with the separate non-lexical outcome state `no-gloss-proposed` (it stays held under the author's own basis until a gloss is proposed and reviewed, and is never recorded as an identity or sense blocker), while every lexical hold basis must be backed by its own axis; and that every ambiguous particle span in an admitted gloss carries the reviewer's own per-span topic verdict, bound to the span's surface and token index (a missing, duplicated, mismatched, or unresolved verdict is never filled in);
- where the raw outputs are staged locally, the validator additionally re-derives the run record and the input from them, so the outcomes and review rows are a mechanical function of the reviewers' original outputs.

What it does not prove: who actually ran the reviewers. B05's candidate dispositions and glosses were written by the earlier `codex-agent` session and its semantic reviews by `claude-sonnet-5-5`. B06's dispositions and glosses were proposed by `claude-sonnet-5-5`; its semantic review was done by three isolated subagent contexts (registered as `claude-sonnet-5-5-independent-reviewer`) that read only the candidate evidence packets, not the proposer's rationale. These are the same model family in separate contexts, and the run records are self-reported by the batch change.

The reviewers' outputs were checked for verbatim corpus text before they were preserved; the few notes and frames that reproduced context phrases were rewritten by the same reviewer contexts, with no verdict changed. The tracked artifacts contain no corpus paragraph text.

## Known provenance limitation (owner override)

The semantic-decision sources for B01–B04 (1,206 records) were produced by the earlier builder, which generated the judgment fields (`gloss_judgment`, single-sense boundary review) itself rather than consuming independently authored reviews. They satisfy the shared validators but do not establish independent editorial review. By owner decision for this checkpoint, they remain as imported; the builder now fails closed for any later batch. Replacing them with independently authored reviews is deferred to separate follow-up work, and later batches, including B05, proceed under the new contract.
